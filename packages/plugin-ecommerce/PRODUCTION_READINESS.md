# Commerce production readiness review

Reviewed on 25 September 2026 against the Talisman CMS integration on Cloudflare Workers and D1, and updated on 26 September 2026 for the incentive and abuse rules.

## Decision

The plugin is suitable for a controlled production deployment with public checkout **disabled**. It is **not ready to accept live orders**. The technical payment safeguards below passed local integration tests, but live payments, tax and delivery policies, operational fulfillment, and a real catalog still need end-to-end verification.

## Safeguards checked

| Area | Evidence and current behavior |
| --- | --- |
| Account ownership | A paid order or a used sign-in link may create or link a shopper account, but the cart cookie cannot activate it. Asking for a link creates no account; the link row keeps only the token hash and the address. A one-time emailed link is consumed before the account is created or linked and a shopper session is issued, and only then is the account linked to the shared CMS user for that email. A link is sent only to a bare address, never to one with a display name. First-order promotions and referrals depend on purchase history, not on whether an account exists. A new user gets the `customer` role, which has no CMS access. Migration `0016` revokes earlier sessions on unverified accounts. |
| Checkout integrity | D1 transactions reserve stock, credit, promotions, and gift card tender with the pending order. Stripe completion must match the stored session, amount, currency, and payment status. Duplicate events do not create a second payment. |
| Recovery | The order status route (at most one provider check per order every 15 seconds, shared with checkout resume and session release, once the order is 60 seconds old) and a ten-minute scheduled Worker reconcile pending Stripe sessions when a webhook is missed. Orphaned preparation locks are released after the configured Stripe session lifetime; gift card purchases are also reconciled. |
| Fulfillment | Migration `0017` restricts fulfillment to a paid, real order and records the administrator, note, and optional carrier and tracking number. Admin test orders cannot be fulfilled. |
| Access | Commerce admin routes require the CMS administrator role and same-origin mutations. Customer cookies are HTTP-only and account link tokens are stored as hashes. An order's status and cancellation are available only to the basket or signed-in account that placed it. The simulated `admin_test` payment provider exists only on sites that set `ecommercePlugin({ adminTestCheckout: true })`, and only the admin route registers it. |
| Basket abuse | The public basket API accepts at most 50 lines of 1 to 99 units, rejects bodies over 64 KB, and stores only catalog products and variants; a product with variant groups is accepted, and sold, only as one of its variant values, never at its base price or as a group that has values. A rejected request creates no basket and reading never creates one. `purgeStaleCommerceData`, run from the scheduled Worker, deletes guest baskets idle for 30 days. Creating a basket is limited to 20 per client network (an IPv4 address or an IPv6 /64) per hour, in the cart route and the `addToCart` action; changes to an open basket are not limited, and checkout never creates a basket. |
| Incentives | Referrals are off until an admin enables them or `TALISMAN_COMMERCE_REFERRALS_ENABLED` is `true` with nothing saved. The reward is at most half the minimum first order, and the minimum applies to the subtotal less the promotion discount. Self-referral and repeat-buyer checks compare exact and canonical addresses. Each referrer, counted across equivalent addresses, has a cap per period. Awards stay pending for a hold period (default 30 days) and the scheduled job releases them only when the payment provider reports no dispute. A refund that leaves the order below the qualifying amount, or a lost dispute, voids the referral and reverses released awards. Discount and gift card code checks share a budget per client network and per basket, and every refused code gets one answer. Stripe checkout coupons are single-use, expire with their session and are deleted when the checkout ends unpaid. |
| Sign-in email | Each address, each network and the store per day are limited. Part of the daily budget is reserved for addresses with a verified account or an order, and once the rest is spent every request gets the same answer. With both Turnstile keys set, a request needs a valid Turnstile token, verified with Cloudflare before any counter, link or email. |
| Verification | `pnpm --filter @talisman-cms/plugin-ecommerce test` passed 195 tests. Route tests cover Stripe signature verification (valid, wrong secret, stale timestamp, changed payload and replay), the checkout-disabled gate on the checkout route, checkout action and gift card purchase, order ownership, basket limits, variant choice, sign-in links and their preview, the Turnstile check and the reserved sign-in budget, referral holds, caps and reversals, discount preview limits and refusals, basket creation limits, the order status throttle and single-use Stripe coupons. The Talisman TypeScript check, Astro production build and a Wrangler deployment dry run passed at the original review. No live payment or remote migration was performed. |

## Launch gates

1. Apply Talisman CMS migrations through `0024_shopper_sign_in_tokens.sql` to the remote D1 database **before** deploying the new Worker; shopper account reads fail without `0019`, and shopper sign-in fails without `0024`. Rehearse rollback from a D1 backup. First confirm that both duplicate checks return no rows. `0018` adds a unique revision index, and `0019` allows one CMS user per email regardless of letter case:

   ```sql
   SELECT entry_id, revision_number, COUNT(*) AS copies
   FROM galaxy_entry_revisions GROUP BY entry_id, revision_number HAVING COUNT(*) > 1;

   SELECT lower(email) AS email, COUNT(*) AS copies
   FROM galaxy_auth_user GROUP BY lower(email) HAVING COUNT(*) > 1;
   ```
2. Replace draft product concepts with verified, saleable products. Confirm actual USD prices, component bills of materials, available stock, images, fit and optical claims, and a physical packing sample.
3. Choose the countries served, delivery charge and time promises, tax treatment, returns and refund policy, and customer contact channel. The current checkout accepts a two-letter country code and treats delivery as included in item prices; it does not calculate tax or shipping.
4. Configure live Stripe keys and a signed webhook for `checkout.session.completed`, `checkout.session.expired`, `charge.refunded` and `charge.dispute.closed`. Before enabling checkout, run one discounted test-mode checkout and confirm that its Stripe coupon `<order id>_discount` has `max_redemptions` 1 and a `redeem_by` equal to the session's expiry, that the session is created without an error on `expires_at`, and that the coupon is deleted after the session expires or the order is cancelled. Delete unused coupons that earlier versions created (random ids) in the Stripe dashboard. Keep the scheduled Worker calling `reconcileCommerce` with the Stripe adapter: it repairs missed webhooks and releases held referral awards. Run a real low-value order through payment, reconciliation, fulfillment, refund, and inventory review before opening checkout broadly.
5. Configure an email provider (a Cloudflare Email Service `[[send_email]]` binding named `EMAIL` on an onboarded sending domain, or a custom provider), the `TALISMAN_EMAIL_FROM` sender and the `TALISMAN_PUBLIC_ORIGIN`. Turn off any provider feature that stores message content, because sign-in links are bearer credentials for 15 minutes. Prove that the checkout email receives a one-time sign-in link and an unrelated browser cannot use the cart cookie to enter that account. Review `TALISMAN_COMMERCE_EMAIL_DAILY_LIMIT` (default 200 sign-in emails a day) against the provider's quota, and `TALISMAN_COMMERCE_EMAIL_RESERVED_DAILY` (default a quarter of it) for existing customers. Create a Cloudflare Turnstile widget in Managed mode for the storefront's hostname, set `TALISMAN_COMMERCE_TURNSTILE_SITE_KEY` and the secret `TALISMAN_COMMERCE_TURNSTILE_SECRET_KEY` together, render the widget from `shopperSignInBotCheck(env)`, and check that a sign-in link still arrives and that a request without a token gets HTTP 403.
6. Assign staff to inspect the admin order queue, pack and label shipments, tell customers about dispatch, resolve failed deliveries, handle refunds, and monitor webhook and scheduled Worker failures. The plugin records fulfillment but does not buy labels or send shipment or order confirmation emails.
7. Keep `TALISMAN_COMMERCE_CHECKOUT_ENABLED=false` until these gates pass. Enable gift card sales separately only after their key backup and purchase, delivery, and refund procedures are tested.
8. Add a Cloudflare rate limiting rule, keyed on the client IP, for every public path under `/api/ecommerce/` except `/api/ecommerce/webhooks/`: today `account`, `cart`, `checkout`, `discount`, `gift-cards` and `order`, for every request method, because a `GET` of `order` for a pending order asks the payment provider for its status. Add `/_actions/*` on sites that use the plugin's Astro actions. Leave the Stripe webhook paths out of every per-IP rule: `/api/ecommerce/webhooks/*`, and `/api/stripe/webhooks` with plugin-stripe. Stripe sends webhooks from a small set of addresses, so a per-IP limit would drop deliveries. Check that the zone's plan supports the counting period and block duration you choose; otherwise use the closest values it allows. On a plan that allows a single rate limiting rule, match all these paths in one rule. The rule is defence in depth next to the plugin's own limits: new baskets per network, code checks per network and per basket, sign-in email per address, per network and per day, and provider checks per order from the order status route, checkout resume and session release. Requests without a client IP are not counted by the plugin's per-network limits.

9. Decide whether referrals run before opening checkout. They are off unless a saved policy or `TALISMAN_COMMERCE_REFERRALS_ENABLED` enables them; check the saved policy with `SELECT enabled, reward_cents, min_order_cents FROM _ecommerce_referral_settings`. Before enabling them, publish referral terms (reward, minimum first order, hold period, cap per period and reversal on refunds and lost disputes), update the privacy and cookie notices for the referral cookie, and show a referred shopper's own pending welcome award, which `getReferralDashboard` does not yet list.

## Known limits

- The referral minimum in force at checkout is not stored on the order. After an admin raises the minimum, a refund is measured against the lower of the new minimum and what the order qualified with at checkout, not against the old minimum. Storing the minimum on the order needs a migration.
- A Stripe checkout coupon is deleted once, when its order is cancelled. If that delete fails it is not retried, and the coupon remains until its `redeem_by`, single-use.
- The referral and first-purchase checks compare canonical addresses by scanning purchased orders; an indexed canonical column needs a migration.

Site deployment steps and secret names belong in each site's own deployment notes; the CMS deployment gate is in [RELEASE.md](../../RELEASE.md#deployment-gate). This review covers the code and local integration; it does not certify the merchant's legal, tax, product, or operational readiness.
