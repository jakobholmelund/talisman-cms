# Admin coverage audit

This audit compares the CMS and bundled plugin APIs with the current admin UI. It covers the core admin and the ecommerce and analytics plugins in this repository. An installing project may add its own collections, plugins, or auth adapter.

| Area | Current admin support | Gap or decision |
| --- | --- | --- |
| Shared users | List with pagination. Local mode can create, reset passwords, change roles, disable, enable and remove CMS accounts. Hybrid mode can add editors, promote verified shoppers with a password and revoke CMS access while retaining the shopper identity. | Implemented in `ui/routes/users.tsx`. Admins can edit local staff names, confirm staff email changes, and inspect or end individual CMS sessions. SSO-managed names/emails and shopper profiles stay read only here; shopper data requests use Commerce. The development adapter has no stored users. |
| Cloudflare Access identities | Access-only mode assigns roles from Worker email allowlists. Hybrid mode exchanges a verified admin identity for a marked CMS session on `/admin/sso`. | There is no admin editor for the allowlist. It is deployment configuration, so changing it requires a Worker configuration update. |
| Webshop users | Email-link registration or sign-in links a verified shopper profile to the shared CMS user identity. Shopper and CMS sessions are separate; a customer role cannot access the CMS. | The admin shows verified shopper identities, but does not edit their order and credit data in Users. Those stay in Commerce. |
| Content entries | Search, status filters, sorting, 50-result pages, create, edit, save draft, publish, archive, and restore revisions | Search uses a configured top-level text field, preferring title/name. Applied filters and the page stay in the URL when opening, creating or saving an entry and returning to the list. Native lists use configured business statuses and available sort fields. Failed reads retain filters for retry. The generic API supports `DELETE /api/collections/:slug/entries/:id`, and the entry editor exposes a confirmed delete action for admins when the collection permits it. |
| Role aware content actions | The API requires admin for publish, archive, restore, and all deletes | Collection rules control create links, save and admin-only publish/archive/restore/delete actions. Read-only fields include rich text and plugin panels; direct new-entry URLs explain why creation is unavailable. Create and update permissions are independent, including the saved submission becoming read-only for its editor. |
| Collections | Code configured collections are listed and editable through their entries | The admin explains that collections are configured in code. Schema management remains a separate product decision. |
| Globals | List, create, and edit | The API has no global delete route, and there is no admin remove action. This appears to be a current data model limitation rather than a missing button. |
| Media | Upload, browse, and edit metadata through the media collection | Upload controls and the upload route enforce collection read/create and read-only rules; generic media creation points to the library. Admins can delete media with backend asset cleanup. A paginated usage report checks drafts, published snapshots, revisions, globals and configured native fields; references or incomplete checks require acknowledgment. Code, external sites and HTML strings are outside its scope. |
| Dashboard | Available collection counts and useful navigation | Unavailable metrics are not shown as placeholder totals. Counts depend on configured collections and read access. |
| Plugin sections | A plugin registers admin sections, editor panels, record describers, exposed settings and stylesheet sources (`Plugin.adminSections` and friends). The core knows no section by name. | Section ids share one namespace across plugins; a collection tagged with an unregistered section falls back to Collections. |
| Ecommerce | The Commerce section, its workspace page, the product editor's Options & stock panel, the model guide and the commerce record labels are provided by `@talisman-cms/plugin-ecommerce`, plus the dedicated orders, promotions, gift cards, checkout, and analytics screens | The generic commerce data models are exposed according to plugin configuration. Some are intentionally read only because payment workflows own their writes. Without the plugin the admin has no Commerce section. |

Email changes need the configured email provider. A 15-minute code goes to the new address and a notification goes to the current address. Confirmation updates linked shopper identities atomically and ends their CMS/shopper sessions without merging accounts or changing historical financial records. Cloudflare Access identities remain managed by their provider.

Further work should follow actual site usage: dedicated global removal semantics, or a searchable media-reference index if measured data size requires it.

Admin navigation and the plugin SDK's URL helpers use a small public configuration containing collection labels, sections, read permissions and links. Full field schemas and UI-library metadata remain separate; the globals editor loads its configuration on demand, and preset authoring loads the component catalog when needed. `e2e/admin-flows.mjs` includes `startup-payload`, which measures three cold Overview loads with browser caching disabled and records per-script decoded/transfer bytes and local timing in the report. The `catalog-loading` flow verifies that Overview does not request editor configuration and that component catalogs load for preset authoring. These checks measure the configured playground, not a deployed site's network performance.

The `collection-permissions` browser flow uses the playground Announcements (admin create), Submissions (admin update) and Managed Notes (read-only) examples. It checks forbidden direct routes, disabled text/rich-text controls, permitted editor writes, preserved admin actions and server refusals for both roles. Policy matrix tests compare the UI capabilities with server user-actor authorization.

The `collection-search-filters` browser flow creates more than one page of real entries. It checks combined server search/status/sort, non-overlapping pages, pagination focus, entry return and creation, reload and browser history, published/archived results, filtered empty states and a failed request followed by retry. It also checks a native plugin collection's configured statuses and filtered query. Filters reset to page one when applied; a clear action returns to the default list. The shared API's offset limit bounds browsing at page 201, after which the UI asks for a narrower search.
