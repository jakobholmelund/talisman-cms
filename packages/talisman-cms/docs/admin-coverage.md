# Admin coverage audit

This audit compares the CMS and bundled plugin APIs with the current admin UI. It covers the core admin and the ecommerce and analytics plugins in this repository. An installing project may add its own collections, plugins, or auth adapter.

| Area | Current admin support | Gap or decision |
| --- | --- | --- |
| Shared users | List with pagination. Local mode can create, reset passwords, change roles, disable, enable and remove CMS accounts. Hybrid mode can add editors, promote verified shoppers with a password and revoke CMS access while retaining the shopper identity. | Implemented in `ui/routes/users.tsx`. Admins can edit local staff names, confirm staff email changes, and inspect or end individual CMS sessions. SSO-managed names/emails and shopper profiles stay read only here; shopper data requests use Commerce. The development adapter has no stored users. |
| Cloudflare Access identities | Access-only mode assigns roles from Worker email allowlists. Hybrid mode exchanges a verified admin identity for a marked CMS session on `/admin/sso`. | There is no admin editor for the allowlist. It is deployment configuration, so changing it requires a Worker configuration update. |
| Webshop users | Email-link registration or sign-in links a verified shopper profile to the shared CMS user identity. Shopper and CMS sessions are separate; a customer role cannot access the CMS. | The admin shows verified shopper identities, but does not edit their order and credit data in Users. Those stay in Commerce. |
| Content entries | Search, status filters, sorting, 50-result pages, create, edit, save draft, publish, archive, compare and restore revisions, review save conflicts | Search uses a configured top-level text field, preferring title/name. Applied filters and the page stay in the URL when opening, creating or saving an entry and returning to the list. Native lists use configured business statuses and available sort fields. Failed reads retain filters for retry. Revision comparisons preserve unsaved edits and are available to readers of read-only entries. Conflict review requires choices for overlapping edits and applies them to the form for a separate guarded save. The generic API supports `DELETE /api/collections/:slug/entries/:id`, and the entry editor exposes a confirmed delete action for admins when the collection permits it. |
| Role aware content actions | The API requires admin for publish, archive, restore, and all deletes | Collection rules control create links, save and admin-only publish/archive/restore/delete actions. Read-only fields include rich text and plugin panels; direct new-entry URLs explain why creation is unavailable. Create and update permissions are independent, including the saved submission becoming read-only for its editor. |
| Collections | Code configured collections are listed and editable through their entries | The admin explains that collections are configured in code. Schema management remains a separate product decision. |
| Globals | List, create, edit, unsaved draft warnings and field choices after stale saves | Both configured fields and raw JSON retain drafts through conflict recovery. Held edits count as unsaved; applying choices updates the draft for a separate version-guarded save. The API has no global delete route, and there is no admin remove action. This appears to be a current data model limitation rather than a missing button. |
| Media | Upload, filename search, file-type filters, cursor pages and metadata editing, in the library and field picker | Upload controls and the upload route enforce collection read/create and read-only rules; generic media creation points to the library. Library filters remain in the URL through asset editing and return; picker searches preserve the selected URL and unsaved fields. Admins can delete media with backend asset cleanup. A paginated usage report checks drafts, published snapshots, revisions, globals and configured native fields; references or incomplete checks require acknowledgment. Code, external sites and HTML strings are outside its scope. |
| Dashboard | Available collection counts and useful navigation | Unavailable metrics are not shown as placeholder totals. Counts depend on configured collections and read access. |
| Plugin sections | A plugin registers admin sections, editor panels, record describers, exposed settings and stylesheet sources (`Plugin.adminSections` and friends). The core knows no section by name. | Section ids share one namespace across plugins; a collection tagged with an unregistered section falls back to Collections. |
| Ecommerce | The Commerce section, its workspace page, the product editor's Options & stock panel, the model guide and the commerce record labels are provided by `@talisman-cms/plugin-ecommerce`, plus the dedicated orders, promotions, gift cards, checkout, and analytics screens | The generic commerce data models are exposed according to plugin configuration. Some are intentionally read only because payment workflows own their writes. Without the plugin the admin has no Commerce section. |

Email changes need the configured email provider. A 15-minute code goes to the new address and a notification goes to the current address. Confirmation updates linked shopper identities atomically and ends their CMS/shopper sessions without merging accounts or changing historical financial records. Cloudflare Access identities remain managed by their provider.

Further work should follow actual site usage: dedicated global removal semantics, or a searchable media-reference index if measured data size requires it.

Globals track form and raw-JSON drafts with an **Unsaved changes** marker and warn before leaving, reloading or closing the tab. After a stale save, **Load latest version** keeps local edits for the shared **Review changes** dialog. Applying choices updates the draft without saving; the next save sends the version loaded with the latest record through `If-Match`, so another writer still causes a recoverable refusal. Held changes remain protected by leave warnings, and Save or Dismiss asks before omitting them. Failed latest reads, invalid JSON and cancelled reviews retain drafts. Fields cannot be edited while a read or write is pending, and responses for an editor that has been left are ignored.

The `globals-draft-recovery` browser flow covers configured fields and an unconfigured JSON document, cancelled navigation and reloads, accepted discard, retry, pending reads, invalid JSON, review focus, nested whole-field choices and repeated version conflicts. Shared comparisons also retain deliberate edits made after loading latest when they return a field to its original value or remove a field introduced by another writer. Global document fields such as `slug` remain ordinary data fields; there is no entry URL-slug choice.

After a stale entry save, **Load latest version** preserves local changes, including edits made after the refusal. **Review changes** displays each edited field's original, local and latest loaded values. Fields both editors changed require a choice; local-only changes default to keeping local values, already-saved values need no choice, and other fields keep their latest saved value. The entry URL slug is separate from a data field named `slug`; native records have only their data fields. Groups, arrays, blocks and virtual preset props are whole-field choices, without positional merging. Rich text and nested content use the same escaped, bounded previews as revision comparison. Reviews page through 20 fields, and unresolved choices on any page prevent applying.

Applying choices only updates the draft form. Save retains the revision ID or native timestamp loaded with the latest version, so a subsequent writer causes another recoverable conflict. Cancellation returns focus to **Review changes** and leaves both form edits and held changes intact; applying returns focus to Save. Invalid raw JSON blocks loading or review until repaired. The `conflict-review` browser flow exercises repeated stale saves, retry, edits made before and after loading latest, keyboard focus, literal rich text, whole block-array choices, native timestamp guards and serialized preset props. The held JSON backup remains available in the conflict panel.

Media filename searches are literal substrings of up to 200 characters. File-type filters match JPEG, PNG, GIF, WebP or AVIF; **All file types** also includes other stored assets. Both filters run on the server before newest-first cursor pages (60 assets in the library, 48 in a field picker), and every subsequent page retains them. Applying new filters resets pagination. Library URL state retains filters, rather than the number of appended pages, when returning from an asset editor.

The `media-search-filters` browser flow uploads 66 real assets, finds an older upload beyond the first page, checks literal search characters and MIME filtering, and verifies complete, non-duplicated cursor pages. It covers reload/back/editor return, empty results, failed reads and retry, and picker pagination with the selected URL, loaded description/filename and unsaved entry fields retained. Picker controls use buttons and a fieldset inside the entry form; Enter applies the filename search without saving the entry. Media reads abort when their view unmounts or a newer read supersedes them.

Revision history initially loads metadata only; **Compare** fetches one snapshot and compares it with the saved version loaded in the editor. Unsaved edits stay outside the comparison. Fields show added, removed, changed or unchanged values, using configured labels and retaining retired fields. JSON object key order is ignored, while array order and rich-text formatting remain significant. Historical content is displayed as text, including nested blocks and optional rich-text structure. Stored revisions do not include the entry's URL slug or author, so the preview does not reconstruct those details. Native tables have no CMS revision history.

The preview shows at most 100 fields, 50 items or values within each nested container, and eight levels of nesting, with explicit omission messages. Comparison checks the full stored content even when the preview is shortened. Failed snapshot reads can be retried; closing cancels pending reads and returns focus to Compare. The `revision-comparison` browser flow checks lazy loading, rich text and labeled blocks, unchanged fields, preserved drafts, focus, retry/cancellation, read-only editor access and the existing confirmed, revision-guarded admin restore.

Admin navigation and the plugin SDK's URL helpers use a small public configuration containing collection labels, sections, read permissions and links. Full field schemas and UI-library metadata remain separate; the globals editor loads its configuration on demand, and preset authoring loads the component catalog when needed. `e2e/admin-flows.mjs` includes `startup-payload`, which measures three cold Overview loads with browser caching disabled and records per-script decoded/transfer bytes and local timing in the report. The `catalog-loading` flow verifies that Overview does not request editor configuration and that component catalogs load for preset authoring. These checks measure the configured playground, not a deployed site's network performance.

The `collection-permissions` browser flow uses the playground Announcements (admin create), Submissions (admin update) and Managed Notes (read-only) examples. It checks forbidden direct routes, disabled text/rich-text controls, permitted editor writes, preserved admin actions and server refusals for both roles. Policy matrix tests compare the UI capabilities with server user-actor authorization.

The `collection-search-filters` browser flow creates more than one page of real entries. It checks combined server search/status/sort, non-overlapping pages, pagination focus, entry return and creation, reload and browser history, published/archived results, filtered empty states and a failed request followed by retry. It also checks a native plugin collection's configured statuses and filtered query. Filters reset to page one when applied; a clear action returns to the default list. The shared API's offset limit bounds browsing at page 201, after which the UI asks for a narrower search.

Orders preserve shipment and correction form details after an unconfirmed or refused write. Shipment retries keep the parcel's request key, and synchronous submission guards send an immediate double submit once. While reads or writes are pending, the fields cannot change. A failed read offers **Retry loading orders**, including the failed next-page cursor; a confirmed write followed by a failed refresh is reported separately and blocks further fulfillment changes until the queue reloads. Superseded search failures are ignored. Order cards have accessible names, and successful pagination/retry places focus on the results summary.

The `orders-workflow` browser flow checks the real local list API and its no-store/admin-test exclusions, then controls response fixtures for exact-ID/email searches kept out of URLs, cursor recovery, partial/final parcels, confirmation cancellation, retained shipment keys, correction history and post-save refresh failures. It never calls live payment providers. The plugin's fulfillment service tests cover database invariants and replay handling.

Promotions preserve independent referral and code drafts, guard immediate double submissions, freeze a pending creation's original details, and confirm before discarding or leaving. Failed reads offer **Retry loading promotions**; a confirmed save remains visible as a success even if its follow-up read fails, and further writes wait for a successful reload. Confirmed code saves reset the creation form while preserving referral drafts. The `promotions-workflow` browser flow performs real local voucher creation and editing, deliberately drops a committed creation's response, retries the same key/payload to recover one voucher, and covers read/write failures, navigation/reload prompts and independent drafts. Referrals remain off; no payment or email provider is contacted. Service tests cover concurrent creation, original actor/payload validation, rollback, spent balances, later edits and append-only request records.

Gift-card issuance keeps a private retry key in page memory until confirmed. Retrying the same details recovers the original code without another card or ledger credit, including concurrent replacement attempts. Codes survive failed list refreshes and refused subsequent issuances; clipboard failures select the code for manual copying. Navigation/reload warns before losing an unconfirmed issuance or an unsaved code. Failed reads offer retry and block further writes. Review refusals reload current refund totals while retaining the staff reason, and gift-card payment refunds require confirmation.

**Replace lost code** on a staff-issued card replaces its bearer code in place, preserving the card ID, balance, suspension and order/refund ledger. Purchased and purchase-backed replacement cards retain their existing tools. A selected card version/balance and staff reason stay in the form; unconfirmed retries use the exact original payload/key even after a refresh, block other writes, and warn before departure or discard. The append-only audit stores hashes/suffixes and staff metadata, with no full codes or private request keys. Original issuance keys cannot recover a subsequently replaced code. Browser coverage commits a real replacement, drops its response, recovers the same new code and checks the old/new codes through the public balance endpoint. Service tests cover later order refunds, one-cent/zero balances, preserved suspension, competing/later replacements and audit rollback. Checkout checks its evaluated code inside the reservation batch; gift-card-only and split-payment races verify rollback, provider cleanup and a successful retry with the current code.

The `gift-card-workflow` browser flow drops the response of a real local issuance after its database commit, then checks recovery of the same card/code, double-submit prevention, list privacy, refresh retry, clipboard fallback and leave warnings. Review and refund checks use controlled responses; no payment or email provider is contacted. On 9 October 2026, all 33 applicable admin browser flows and 455 commerce tests passed, including 30 gift-card tests; the opt-in hybrid-editor rehearsal was skipped. Plugin type checks and the linked site's checks, 52 tests and build also passed. Neither browser storage nor the card list stores the private retry key or exposes full codes.

The `new-entry-collapsed-cards` browser flow creates a real page with a collapsed block and nested component, saves it, and checks that both stay collapsed after the editor remounts and reloads. The storage scope moves from the draft to the saved ID; the next new page does not inherit the old preferences. Helper tests cover multiple fields, the 50-entry cap and unavailable/full storage.

On 9 October 2026, separating collection screens from route loaders and extracting lightweight relationship metadata reduced cold Overview JavaScript from **487,906 to 400,113 decoded bytes** (18%). Each build was measured three times in fresh authenticated Chrome contexts with its network cache disabled against the local playground preview. Median Overview-visible timings were 97 ms before and 94 ms after; these localhost samples do not establish a speed improvement. The `catalog-loading` browser flow verifies that validation and collection-screen chunks remain deferred on Overview and that component catalogs are still loaded only for preset authoring. All 31 applicable browser flows, 392 core tests, 14 fulfillment service tests, and core/plugin type checks passed. Public helper exports and database schemas are unchanged.
