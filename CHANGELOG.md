# Changelog

## Unreleased

### Breaking changes

- `migrations_dir` no longer points at the core package's `drizzle` folder. The integration copies the core's migrations and every registered plugin's into one folder, `node_modules/.talisman-cms/migrations` by default (the `migrationsDir` integration option moves it), on every `astro sync`, `astro dev`, `astro build` and `astro check`. Point the `DB` binding's `migrations_dir` there and run `pnpm exec astro sync` or a build before `wrangler d1 migrations apply`. A build fails with the fix while a plugin ships migrations and a `migrations_dir` still names the core folder. Existing databases have nothing new to apply: every file keeps its name, and wrangler ignores applied names that are no longer in the folder.
- The ecommerce plugin ships its own migrations from `0025_order_shipping_and_tax.sql` on, in `@talisman-cms/plugin-ecommerce/drizzle`. The core's `drizzle/` folder ends at `0024` and stays as the 0.1 baseline: it still creates the commerce tables of that time, because `0019` changes CMS and commerce tables in one file and applied names cannot change. A site without the ecommerce plugin gets those tables and never the later ones. Tests that read migrations from the core folder by name resolve `0025` to `0030` from the plugin's folder.
- `AdminSection` is a string. The admin's `commerce` section exists only when a plugin registers it (`ecommercePlugin()` does), collections are grouped by their `adminSection` alone (the `_ecommerce_` prefix and the plugin schema path are no longer inferred, and a collection whose section is not registered is listed under Collections), and `<meta name="talisman-commerce-currency">` is replaced by `<meta name="talisman-setting-commerce-currency">`, one of the settings a plugin declares with `adminSettings`; its content is the raw setting, empty when unset.

- A plugin `adminLinks[].href` or `routes[].path` that is not a path on the site, such as a full URL or a `//host` form, now fails the build with the plugin's name. A value without a leading slash is relative to the admin path.

### Plugins

- `Plugin.onInit` is optional and typed: it receives a `PluginConfig`, the site's options with `collections`, `globals` and `plugins` always present and `adminPath` normalized, may mutate it and return nothing or return a new config, and the options object the site passed in is left unchanged. `TalismanCmsOptions` and `PluginConfig` are exported from `talisman-cms`.
- `talisman-cms/ui/sdk` gives plugin admin code `adminPath`, `adminUrl`, `adminApiUrl`, `adminRequest`, `readAdminSetting` and `useAdminUser`. The ecommerce, analytics and daisyUI screens use it instead of reading the admin path from `window.location`, so they follow a custom `adminPath`; the ecommerce and analytics links and the daisyUI preview route (`daisyui-preview`) are declared relative to the admin path.
- `Plugin.scheduled: { moduleId, exportName? }` names a server module the Worker's scheduled handler runs on every cron tick. `talisman-cms/worker` exports `scheduled`, `runScheduledJobs`, `ScheduledJob` and `ScheduledJobEvent`: the handler runs every plugin's job in registration order, logs each failure as `[talisman-cms] <plugin> scheduled job failed: <message>`, never skips the next job, and fails the invocation afterwards. A site names a Worker entry (`main` in `wrangler.toml`) that exports `{ fetch: handle, scheduled }` and sets `[triggers] crons`; the integration warns when a plugin declares a job and no wrangler config has a cron trigger. The playground's `src/worker.ts` is the reference entry.
- [Build a plugin](packages/talisman-cms/docs/build-a-plugin.md) walks through the plugin contract.
- `Plugin.migrations: { dir }` contributes numbered SQL files, and `talisman-cms/migrations` exports `listMigrationSources`, `assembleMigrations` and `compareMigrationNames`. One sequence of numbers runs across the core and every plugin; a shared name or number fails the build. The assembled folder carries a `sources.json` naming each file's package, and the assembler replaces or removes only files it wrote itself: a `.sql` file it did not write fails the build instead of being deleted, so a site's own migrations belong in another folder.
- Plugins register admin sections (`adminSections`: a sidebar entry, the routes `/<id>`, `/<id>/<slug>` and `/<id>/<slug>/<entryId>`, an optional workspace page, and `adminOnly` for sections whose tools need the admin role), editor panels (`adminEditorPanels`, rendered before the fields or after the form for the collections they match), record labels for relation pickers and summaries (`adminEntryDescribers`), settings exposed to the admin page (`adminSettings`; the page is served before sign-in, so only display settings belong there, a name that looks like a secret is refused at config time and a value that reads like a key is left out) and folders Tailwind scans for the admin stylesheet (`adminStyleSources`). Fields with `saveOnlyIfChanged` are sent only when the user changed them. The core README's "Plugin admin extension points" section describes the contracts.

### Admin

- The globals editor sends the version it loaded with every save (`If-Match`). When another editor saved first, the edits stay in the form, a panel says so, and **Load latest version** replaces them with what is stored, after asking. The entry editor publishes and archives from the revision its own save returned instead of re-reading the entry first, so a publish right after a save cannot land on a newer revision someone else saved in between, and one request per publish or archive disappears.
- Native records with a `name` show it in the editor heading, list rows without a naming field read `<Collection name> <id tail>`, a collection opened under a section it does not belong to shows "Collection Not Found" inside the admin, an unknown top-level path shows "Section Not Found", and editors who open an admin-only section's URL see "Admin access required". The products list and editor use the generic record wording; the product-specific labels and the details/options anchor navigation are gone.

### Globals

- Every global carries a `version` that grows by one with each save; migration `0031_global_versions.sql`, in the core, adds the column with 1 for existing rows. `GET <adminPath>/api/globals/:slug` answers with `version` and an `ETag`, and `POST <adminPath>/api/globals/:slug` takes the loaded version in `If-Match`, bare or quoted: a version that moved on answers HTTP 409 with `{ error, code: "stale_record", version }`, a value that is not a version 400, and a save without the header writes unconditionally, as before. The check and the increment are one statement, so two saves that name the same version cannot both win. `getClient(env).globals.save(slug, data, { expectedVersion })` does the same and throws a `ConflictError` whose `code` is `stale_record` and whose `version` is the stored one; `globals.update` stays as the older name. `ServiceErrorCode` gains `stale_record`, and `ConflictError` takes `{ code, version }`.

### Authentication and users

- The Cloudflare SSO sign-in (`HybridAuthAdapter`, `<adminPath>/sso`) mints the CMS session directly after the Access JWT is verified, through a better-auth plugin endpoint that reads the token from the request headers itself and is not reachable over HTTP. It no longer derives a password from the auth secret, stores it as a credential and hashes it on every login: an SSO-managed admin has no password credential, a credential stored by an earlier version is deleted on the admin's next sign-in, and the auth secret signs session cookies and nothing else. Existing SSO sessions keep working, and a new sign-in no longer ends the admin's other sessions; it prunes the ones that have expired or passed the 7-day age cap, so the rows per admin stay bounded. The endpoint is marked server-only, so better-auth's own router never serves it either. An allowlisted email whose row is an editor or a shopper becomes an admin on its SSO sign-in, as before, and loses any password credential.
- The integration passes its `adminPath` to the auth adapter when the Worker loads it (`__talismanAuthRuntime.adminPath`), so `LocalAuthAdapter()`, `HybridAuthAdapter()` and `AccessAuthAdapter()` take no path. A path passed anyway is accepted when it matches and fails the build when it does not.
- Better-auth's default role is `customer`: a user created without an explicit role has no CMS access. Every built-in path names its role.
- `GET <adminPath>/api/auth/setup` answers `{ required: false }` under hybrid, Access and dev auth instead of HTTP 404, so the sign-in panel no longer logs a failed request on every load. Setup itself stays unavailable outside local auth.

### Ecommerce plugin

- The product editor's **Options & stock** panel loads only the product's variant groups, values, stock and component rows, through the entries API's `where` filter, instead of every row of those tables and the products table; the commerce describer no longer asks the editor to load the product flow for products. A refused read shows as an error rather than an empty product.
- The plugin's plain reads and writes go through Drizzle, with row types from its schema, instead of raw SQL with hand-written row shapes: sign-in links and rate-limit reads, gift card purchase and claim reads and writes, email delivery claims and outcomes, tax sync bookkeeping, order lookups before a shipment or restock, and basket unlocks and the checkout lock. Raw SQL stays where the query builder cannot express the statement (batches, `INSERT ... SELECT`, subqueries, dynamic tables, the stale-write guards and the selections that need literals for their partial indexes); CLAUDE.md's "Database access" section states the rule. No behaviour changes.
- `@talisman-cms/plugin-ecommerce/scheduled` is the plugin's scheduled job, registered through `Plugin.scheduled`: on every tick it runs `reconcileCommerce` with `runtimePaymentAdapters(env)` and then `purgeStaleCommerceData`, independently, with the `[Commerce] Checkout reconciliation failed` and `[Commerce] Data retention cleanup failed` log lines, and fails the tick when either failed. A site no longer wires the two functions into its own handler; it exports the handler from `talisman-cms/worker` in its Worker entry (see the plugin README's step 5). The functions stay exported for a handler of your own.
- The Commerce admin reads the configured `productsCollectionSlug` from `virtual:talisman-cms/ecommerce-admin`; record labels, the editor's related-record loading, the model guide, the flow summary and the workspace groups followed the slug `products` before. An `adminPages` override may be a path relative to the admin path or an absolute path on the site; a full URL now fails the build.
- The Commerce workspace, the product editor's **Options & stock** panel with its storefront preview, the model guide of the catalog collections, the labels of commerce records in relation pickers and the store currency reader now come from the plugin (`src/admin/`). URLs, headings and controls are unchanged; the panels load when first shown. Every plugin collection is tagged `adminSection: 'commerce'`, and the four inventory fields carry `saveOnlyIfChanged`.
- The plugin's `test/migrations.test.mjs` assembles the core's and the plugin's migrations, checks that the sequence `0000` to `0030` is unchanged, applies it as wrangler does to a fresh database and to a seeded one recorded at `0024`, and holds the tests of `0025` to `0030` that lived in the core.

## Release candidate: talisman-cms 0.1.0 and plugins 0.0.1

- Initial publishable Talisman CMS packages for Astro and Cloudflare D1, with optional R2 media and KV caching.
- Draft, publish, archive, and restore transitions retain revisions atomically. Admin API clients now send `expectedRevisionId`; stale changes return HTTP 409.
- Media uploads accept bounded raster images validated by file signature. Legacy active uploads are served as downloads with restrictive headers.
- Collection access rules restrict native commerce tables to administrators. Cart and customer records are read-only in the generic CMS editor.
- Adds the analytics plugin and package archive checks to CI. Package manifests and archives use Apache-2.0.
- Adds `HybridAuthAdapter` (`talisman-cms/auth/hybrid`): local passwords for editors and Cloudflare Access SSO for allowlisted admins. The new `<adminPath>/sso` route (normally `/admin/sso`) verifies the Access JWT and issues the admin's CMS session; protect only that path with Access.
- Adds `talisman-cms/auth/identity`. Its `ensureVerifiedEmailIdentity` finds or creates the single CMS user for a verified email. New users get the `customer` role, which has no CMS access.
- Migration `0019_shared_customer_identity.sql` adds `galaxy_auth_session.auth_method` and `_ecommerce_customer_accounts.cms_user_id`, lowercases CMS user emails, and enforces one CMS user per email regardless of letter case. It links shoppers who have already verified their email to `customer` users. It fails if two CMS users' emails differ only by case; run the pre-check in the [release checklist](RELEASE.md) first.
- Shoppers can create an account with an email sign-in link before any purchase. Asking for a link creates no account: using it creates the account, already verified, or reuses the existing one, and links the shopper to the shared CMS identity. Links go only to a bare address. Each address can ask for three links per ten minutes and each source IP (IPv6 per /64) for 20 per hour, within a store-wide daily limit, part of which is kept for addresses with a verified account or an order. An optional Cloudflare Turnstile check can be required before any link is sent. Shopper sessions remain separate from CMS sessions.
- The ecommerce plugin enforces launch rules for incentives and public endpoints: referrals are off by default and their awards stay pending for a hold period, the discount preview and basket creation are rate-limited, public order requests (status, checkout resume and session release) ask the payment provider at most every 15 seconds per order, and Stripe checkout coupons are single-use and expire with their session. These rules need no migration beyond `0024`.
- The ecommerce plugin sells in a configurable store currency, checks the delivery country, charges shipping rates and calculates tax with Stripe Tax, all set with `TALISMAN_COMMERCE_*` settings, and pins Stripe's presentment currency to the order currency. A store that sets none of the new settings sells in USD, delivers to any country and charges no shipping or tax, as before. Migration `0025_order_shipping_and_tax.sql` records shipping and tax on orders. The admin, the storefront components, analytics and the playground format money by each currency's minor units.
- The ecommerce plugin supports a store's daily order operations. Fulfillment is recorded apart from payment, with split shipments, corrections and a server-side queue of every order to ship. Stripe disputes hold their orders, and a lost dispute refunds the order. Refunds are dated, and an audited restock returns their stock. Reconciliation backs off failing checkouts and parks permanent failures for an administrator's decision. Order confirmations, shipment notices and one-time gift card claim links are emailed. Gift card purchases held for review can be resolved, lost cards replaced and the gift card key rotated. Migrations `0026_order_fulfillment_status.sql` through `0030_commerce_order_emails.sql` add their columns and tables. The product editor saves option values with their stock in one batch, and checkout reads a basket's catalog in a fixed number of statements.
- **Users** can change roles, disable, enable, and remove local accounts. In hybrid mode it adds editors, grants a verified shopper editor access with a password, and revokes CMS access instead of removing the shared identity.
- The admin's entry and globals editors share one field renderer (`ui/components/fields`). Globals gain the media field, both editors trim ISO dates for the date input, the storefront preview and the server error summary follow typing, and collapsed page builder cards are kept under one localStorage key per entry (50 entries at most) instead of one key per field.
- The admin bundle is code-split: each route's component, the rich text editor (Tiptap), the page builder and every plugin admin page load when first used, so a plugin's `adminUi` component module is evaluated when its page is first opened rather than at start-up. In the playground build the admin's entry chunk drops from 1,433 KB to 294 KB.
- The admin sidebar opens as a drawer below the `md` breakpoint from a header button; from `md` up it is unchanged.
- `pnpm e2e:admin` (`e2e/admin-flows.mjs`) drives the admin's editing flows in Chrome with playwright-core against a built playground, and the GitHub workflow runs it after the playground build (see RELEASE.md).
- The admin API handler and `getClient` are built on one service layer (`packages/talisman-cms/src/service`). Hooks, validation, access rules and cache invalidation run there once, for every caller: every service call carries an actor (`user` for the admin API's signed-in editor or administrator, `system` for server code such as the SDK), the authorization rules apply to users and the integrity rules to everyone. `getClient` keeps its methods and options; `talisman-cms/client` also exports `createService`, `systemActor`, `userActor` and the error classes. Every versioned write answers with `latestRevisionId`. `test/service-parity.test.mjs` runs the same scenarios through the admin API and the service and requires the same rows, cache deletes, hook calls and outcome.
- Collection rows are memoized per isolate, so neither the admin API nor `getClient` looks a collection up in D1 on every read. The KV cache lives in one module with three exported helpers, `invalidateEntryCache`, `invalidateGlobalCache` and `invalidateCollectionCache`, and is cleared from every write path, including the media upload and the collection sync, which cleared nothing before. Native collections are cached only on request, for a minute.
- Entry lists take `where`, `sort` and `offset`: `GET /admin/api/collections/:slug/entries?where[productId]=<id>&where[status][in]=draft,published&sort=-createdAt&offset=20&limit=50`, and `getClient().entries.findMany(slug, { where, sort, offset, limit })`. Field names must be configured or system fields, operators must fit the field's type, and values are bound, never spliced into SQL. The admin's `fetchEntriesWhere` helper pages through a filtered list.
- The admin's editing flows are more accessible. Controls stay focusable while a request runs (`aria-disabled` and `aria-busy` with a status line instead of `disabled`); saves, publishes, restores and variant changes are announced ("Draft saved.", "The entry is published.", "Revision N restored."); the conflict panel, error summaries and outcomes take focus; the error summary's field names focus their fields; repeated buttons name the record, field or revision they act on; the rich text toolbar is one tab stop with arrow keys; styled text became headings; read-only records disable their controls for the keyboard too; the shell has a skip link and moves focus to the page on navigation; and the **Users** screen confirms a role change from a "Change role" button next to the select instead of on every change of the select.

### Breaking changes

These changes can break a site, integration or API client built against the pre-release source, for example through `link:` or a git checkout. Each entry says what to do; the sections below have the details, and [Upgrading](#upgrading) gives the order of the steps.

#### Deployment and settings

- Apply the new D1 migrations, `0019_shared_customer_identity.sql` through `0030_commerce_order_emails.sql`, before deploying the matching Worker, as the [release checklist](RELEASE.md#deployment-gate) describes. `0019` fails while two CMS users' emails differ only by letter case, and `0023` while two published entries in a collection share a slug, so run their pre-check queries first. Without `0019`, local and hybrid CMS sign-ins and shopper account reads fail; without `0021`, every entry read and save fails; without `0024`, shopper sign-in fails; without `0025`, every ecommerce order read and the Commerce analytics fail, because the plugin's Drizzle `orders` table names the new shipping and tax columns. Every ecommerce order read also needs `0026` and `0029`, and gift card reads need `0027` and `0029`; without `0028`, order refund and dispute webhooks fail, and without `0030`, payment confirmation, shipments and gift card purchases fail. `0022` moves global data that is not a JSON object under a `value` key (see [Site code and plugins](#site-code-and-plugins)).
- Worker settings, secrets and the default Workflow binding are renamed from `GALAXY_*` to `TALISMAN_*`, for example `TALISMAN_AUTH_SECRET` and `TALISMAN_PUBLISH_WORKFLOW`. The old names still work but log a deprecation warning. Rename each one and keep its value.
- The CMS no longer reads a `QUEUE` binding. `getClient().tasks.enqueueImageProcessing` and the `QUEUE` entry of `TalismanEnv` are removed; remove the calls, and the binding if nothing else uses it.
- Shopper sign-in email needs an email provider, normally a Cloudflare Email Service `[[send_email]]` binding named `EMAIL`, plus a sender (`TALISMAN_EMAIL_FROM` or `TALISMAN_COMMERCE_EMAIL_FROM`) and a public origin (`TALISMAN_PUBLIC_ORIGIN` or `TALISMAN_COMMERCE_PUBLIC_ORIGIN`). Built-in Resend support and `RESEND_API_KEY` are removed; register another HTTP email API as a custom provider.
- `DevAuthAdapter` fails `astro build` and `astro preview`, and refuses a dev server exposed with `--host` or `server.host`. Use `LocalAuthAdapter`, `HybridAuthAdapter` or `AccessAuthAdapter` for anything other than `astro dev` on localhost.
- CMS sessions end 7 days after sign-in, even while in use.
- Sites that take Stripe payments through the ecommerce plugin add `charge.dispute.created` and `charge.dispute.closed` to the events their Stripe webhook endpoint sends to `/api/ecommerce/webhooks/stripe`, so a dispute holds its order and a lost one refunds it and reverses referral awards. After the deploy, send again from the Stripe dashboard the `charge.dispute.created` event of every dispute that is still open. The scheduled Worker must call `reconcileCommerce` with the Stripe adapter (`runtimePaymentAdapters(env)`), which now also releases held referral awards and retries order emails.
- Sites that take orders through the ecommerce plugin configure email for order confirmations, shipment notices and gift card claim links: the provider and sender that sign-in links use, an https `TALISMAN_PUBLIC_ORIGIN` for claim links, and the optional store details and policy links (see the [ecommerce README](packages/plugin-ecommerce/README.md#order-emails)). Until then `reconcileCommerce` reports the waiting emails as `error` results, which fail a scheduled handler that throws on errors.
- Referrals now depend on a saved referral policy or on `TALISMAN_COMMERCE_REFERRALS_ENABLED` (see [Ecommerce plugin](#ecommerce-plugin)). Before deploying, check the saved policy with the read-only query `SELECT enabled, reward_cents, min_order_cents FROM _ecommerce_referral_settings`. A row with `enabled = 1` keeps referrals on after the upgrade; no row means they are off.

#### Packages

- `talisman-cms` requires Astro 7 (it accepted Astro 5 and 6 before) and Node 22.12 or later. `drizzle-orm`, `react` and `react-dom` are peer dependencies of the core, so the site installs them. Plugins take `talisman-cms` and `astro` as peers, plus React or drizzle-orm where they use them.
- `@talisman-cms/plugin-stripe/routes/*` resolves to built JavaScript in `dist/` instead of TypeScript source. Import `.../routes/webhooks`, without `.ts`.
- Upgrade `talisman-cms` and `@talisman-cms/plugin-ecommerce` together: the product editor's **Options & stock** saves through the plugin's new `variants` endpoint, and the plugin imports `invalidateEntryCache` from `talisman-cms/client`. With an older plugin, option saves get HTTP 404.

#### Admin API clients

- Entry responses return `slug` as the slug being edited, which for a published entry can be a pending rename, and add `publishedSlug`, the live slug. Read `publishedSlug` for an entry's live URL.
- Entry slugs are unique within a collection, and client-chosen ids and slugs must follow the format rules. Creating an entry with, or renaming one to, a slug another entry uses or has pending returns HTTP 409, as does publishing onto a slug another published entry serves. A malformed id or slug returns 400.
- HTTP 409 no longer always means a stale edit: slug conflicts and unique or foreign-key constraint failures return it too. Reload only after a stale `expectedRevisionId` or `expectedUpdatedAt`, and otherwise show the response's `error`.
- With a publishing Workflow binding, a publish or archive that is still running after 10 seconds returns HTTP 202 with the entry as stored before the transition, `workflow: { status: 'pending', instanceId }` and a `message`, instead of an error. The Workflow finishes on its own; reload the entry to see the result.
- Validation errors return `{ error, fieldErrors, issues }`, with a summary in `error` instead of `Validation Error` (or `Validation failed` for globals). Required fields reject blank and whitespace-only values, and publishing validates the draft against them, so an entry saved with a blank required field must be completed before it can be published.
- An optional field sent as `''` is stored as no value: `NULL` in a nullable native column, the default or stored value in a `NOT NULL` native column that is not text, and `null` for an optional number or select in entries and globals. Read such fields as possibly `null`, not `''`.
- Client errors that returned HTTP 500 with the error's message now return 4xx: invalid JSON 400, an unknown collection, entry or revision 404, a constraint failure 409 or 400, and a body over 2 MiB 413. Other 500 responses and the health check no longer include error details; the Worker log has them.
- `GET .../entries/:id/revisions` returns revision metadata without `data`. Add `?includeData=true`, or load one revision with `GET .../revisions/:revisionId`.
- Globals return `data` as a JSON object instead of a JSON string, and `POST /admin/api/globals/:slug` rejects data that is not an object (400). Creating a global that is neither configured nor stored needs an administrator (403 for editors).
- Native collections: a create or update that sets a table column outside the configured `fields` returns 400 instead of storing it. Media records cannot be created through the entries API (403), and their `url` and `mimeType` cannot be changed (400).
- `POST .../entries`, `PUT .../entries/:id`, publish, archive and restore answer with `latestRevisionId`, the revision the write created, so a client can chain its next save or publish without re-reading the entry (additive). A create on a native table whose id column has its own default (`$defaultFn` or an integer key) keeps the table's id, where the API used to generate a text id; no shipped table is affected.
- `GET .../entries` takes `where[field]=value`, `where[field][op]=value` (`eq`, `ne`, `in`, `lt`, `lte`, `gt`, `gte`, `contains`, `isNull`), `sort` and `offset`. An unknown field or an operator the field's type does not take returns 400 with the field in `fieldErrors`. A `sort` or `offset` pages by offset and comes back without `nextCursor`; `cursor` works only with the default order.
- Auth API: in hybrid mode, password sign-in with an SSO admin's or a shopper's email returns 401 instead of 403. With `LocalAuthAdapter`, a `customer` account that has a password gets 401 and no session. A disabled account that signs in with its correct password gets 401, like a wrong password, instead of 403. Admin actions with a non-string `userId` or `role` return 400.
- `GET /admin/api/ecommerce/fulfillment` returns one page of the orders queue, `{ view, pageSize, awaitingCount, nextCursor, orders }`, instead of `{ orders, fulfillments }`, and takes `view`, `cursor`, `limit` and `query`. Each order adds `fulfillmentStatus`, `canShip`, `items` with product names and SKUs, labelled `amounts` and `shipments` with their corrections. `POST` takes an `action` (`list`, `ship` or `correct`); a body without one that names an `orderId` still records a completing shipment. Invalid input gets HTTP 400 instead of 409. Search by email with the `list` action, which keeps the address out of URLs.
- `POST /admin/api/ecommerce/reconcile` takes the actions `retry` and `release`; a body without an action still runs reconciliation, but a body that is not a JSON object, or not valid JSON, gets HTTP 400.

#### Site code and plugins

- `getClient().globals` returns `data` as an object, also for rows and cache entries written by earlier versions, which returned a JSON string. Remove any `JSON.parse` of it. Migration `0022` keeps stored data that is not an object, such as a list, under a `value` key, so code that read such a global reads `data.value`. `globals.create` and `globals.update` throw a `TypeError` for data that is not a JSON object instead of storing it.
- `getClient().entries.create` and `update` return `slug` as the slug being edited and add `publishedSlug`, and throw `SlugConflictError`, exported from `talisman-cms/client`, for a taken slug, also when they publish through a Workflow binding. In draft mode, `entries.findBySlug` finds an entry with a pending rename by its new slug only. Published reads are unchanged.
- When `entries.create` or `update` publishes or archives through a Workflow binding that is still running after 10 seconds, it returns the entry as stored before the transition with `workflow: { status: 'pending', instanceId }` instead of throwing. Check for `workflow` before treating the entry as published.
- Relationship fields resolve only entries of the relation's target collection, and leave ids of collections that only administrators may read unresolved.
- `getClient().entries.create` and `update` validate the data against the collection's fields, check client-chosen ids and slugs, and run the collection's hooks, as the admin API does; they throw `ValidationError`, `InvalidInputError` or `HookError` (all exported from `talisman-cms/client`) instead of writing. A `status` of `published` or `archived` publishes from the save's own revision and refuses an incomplete draft with `ValidationError`. Fix the data, or catch `ValidationError` and read its `issues`. Server code may still write any native column and leave the revision token out; pass `{ actor: userActor(user, request) }` as the third argument of `getClient` to get the admin API's rules instead.
- `getClient` errors are typed: `globals.create` and `update` throw `ValidationError` (was `TypeError`), `InvalidInputError` (was `Error`) or `ConflictError` (was `Error`) with unchanged messages; `entries.update` of a missing native row and `entries.delete` of a missing record throw `NotFoundError` (delete returned `true`); an invalid `limit` throws `InvalidInputError` (was `RangeError`). Code that matched `error.name` or `instanceof TypeError` changes; code that reads `error.message` does not.
- Native collection reads through `getClient` (`findMany`, `find`) are no longer cached in KV by default: plugin SQL writes them without clearing anything, so a copy could be stale for an hour. Pass `cache: true` for a 60 second copy; `invalidateEntryCache` still clears it. Entries and globals keep their hour-long cache.
- Collection hook arguments change: `actor` (`{ kind: 'user', user, request }`, `{ kind: 'system' }` or a reserved `plugin`) and `collection` (`{ slug, native }`) are added and `req` becomes optional, since SDK writes have no request. Replace checks on `req` with `args.actor` (`actor.kind === 'user' ? actor.user.role : 'admin'`). A hook that throws one of the exported error classes refuses the write with that status; any other throw still answers 500 with its message. `@talisman-cms/plugin-stripe` is updated in the same release: administrators and server code may delete Stripe-linked records, editors may not.
- `virtual:talisman-cms/collection-hooks` is a tsup external of the core, so a site's hook modules are bundled once, by Vite, and `dist/client.js` reaches them through the same virtual module inside the Worker.
- Deleting a media record deletes its file from R2. Pages that still use the file's URL get HTTP 404 once cached copies expire, which takes at most an hour now that media responses are no longer cached as immutable for a year. Replace a file's uses before deleting its record.
- Plugin endpoints without `public: true` (served under `<adminPath>/api/`) and plugin pages under the admin path need a CMS session: endpoints answer HTTP 401 and pages redirect to the admin sign-in. An endpoint that must stay public needs `public: true`, which serves it under `/api/`. Mark an admin-path page that anyone may open with `public: true` too; the `Plugin` type's `routes` items now declare it. Prerendering an admin-path page that needs a session fails the build.
- The admin SPA's browser copy of `virtual:talisman-cms/config` leaves out `runtimeHooks`, the `publishing` binding, and keys or values that look like secrets. Custom admin screens that need them read them on the server.
- The admin broadcasts `TALISMAN_ENTRY_SAVED` instead of `GALAXY_ENTRY_SAVED` on the `talisman-cms-preview` channel. `LivePreview` accepts both; custom preview listeners must accept the new type.

#### Ecommerce plugin

- Sign-in links carry the token in the URL fragment (`/account/verify#token=…`). Custom verify pages read it with `readCustomerSignInToken()` from `@talisman-cms/plugin-ecommerce/browser`.
- The account API returns HTTP 503 instead of 400 when a sign-in email cannot be sent.
- Once the general part of the new daily sign-in email limit is spent, `POST /api/ecommerce/account` with `{ email }` answers HTTP 200 `{ accepted: true, limited: true }` for every address, and only addresses with a verified account or a purchased order are still sent a link, from the reserved part. Show a neutral message for `limited: true` ("sign-in emails are limited today"); there is no 503 for the daily limit. The server helper `requestCustomerEmailSignIn` returns `Promise<{ limited: boolean }>`, takes an optional sixth argument `{ waitUntil, onLimitedSendError }`, and no longer throws `CustomerEmailLimitError`, which stays exported. The browser helper resolves to `{ accepted: true, limited?: true }`.
- With `TALISMAN_COMMERCE_TURNSTILE_SECRET_KEY` set, sign-in email requests without a valid Turnstile token get HTTP 403 "The security check failed. Please try again." A site that sets the secret must render the widget from `shopperSignInBotCheck(env)` and pass its token as `requestCustomerEmailSignIn(email, { turnstileToken })`. Nothing changes while the secret is unset.
- Referrals are off by default. With no saved referral policy they run only when `TALISMAN_COMMERCE_REFERRALS_ENABLED` is `true`; before, they ran whenever no policy was saved. To keep them, save the policy under **Commerce → Promotions** or set the setting. A saved policy wins over the setting in both directions. The reward may be at most half the minimum first order: `saveReferralSettings` refuses to enable a larger reward, and invalid input now throws an `Error` whose message joins the validation messages instead of a `ZodError`. Terms that break the rule, from Worker settings or an older saved row, pause new referrals.
- Referral awards are no longer credited at payment. Payment records the referral as pending, and the scheduled `reconcileCommerce` (or `releaseReferralAwards`) credits both shoppers once the hold has passed (`TALISMAN_COMMERCE_REFERRAL_HOLD_DAYS`, default 30 days) and the payment provider reports no open or lost dispute. A first order qualifies when its subtotal less the promotion discount reaches the minimum; before, the subtotal alone counted. A refund of any size that leaves the order below the qualifying amount, or a lost dispute, voids the referral and reverses released awards; before, only a full refund did.
- `getReferralDashboard` returns `code: null` while referrals are off and the shopper has no code, and no longer creates a code then; an existing code is still returned. Each `earned` entry adds `state` (`'pending' | 'released' | 'void'`) and `releasesAt` (a `Date` for a pending award, otherwise `null`); show pending awards as not yet spendable. `creditBalance` excludes pending awards. `referralPolicy()`, `getReferralPolicy()`, `getPromotionsAdmin().referral` and `saveReferralSettings` return `{ enabled, switchedOn, termsError, source, rewardCents, minOrderCents, attributionDays, holdDays, maxPerPeriod, periodDays }`, where `enabled` now means that new referrals are attributed.
- `reconcileCommerce` adds results with the statuses `referral_released`, `referral_void`, `referral_held` and `unchanged`, whose `id` is a referral id, and `{ id: 'referral_awards', status: 'error' }` when a release run fails. Treat only `status: 'error'` as a failure.
- `POST /api/ecommerce/discount` answers every refused discount or gift card code with HTTP 409 `{ error: 'This code is not valid for this order.', field: 'code' | 'giftCardCode' }`, instead of a message per reason; a code of the wrong shape gets the same answer instead of 400. It accepts `customerEmail` but ignores it: first-order and per-customer rules are checked against a signed-in shopper's account, and for a guest only at checkout, so a guest's preview can price a code that checkout then refuses. It no longer creates a basket; a missing, empty or locked basket gets 409 "Basket is not available for discounts".
- Code checks are rate-limited: the discount preview and every checkout that carries `discountCode` or `giftCardCode` share 30 checks per client network (an IPv4 address or an IPv6 /64) and 10 per basket per hour. Over either limit the routes answer HTTP 429 `{ error: 'Too many code checks. Please try again later.' }` and the `checkout` action throws `ActionError` `TOO_MANY_REQUESTS`. Handle a 429 from checkout as well as from the preview.
- `POST /api/ecommerce/checkout` answers a refused discount or gift card code, including one used up while the order is reserved, with the same 409 body. The `checkout` action throws `ActionError` `CONFLICT` with that message instead of `BAD_REQUEST` with the reason.
- The checkout route and the `checkout` action use only the shopper's open basket and never create a basket or set a basket cookie. Without a basket cookie the route answers HTTP 400 "No cart session found"; with a cookie but no open basket with items it answers HTTP 400 "Cart is empty". The action throws `BAD_REQUEST` "Cart is empty or not found" in both cases. The action no longer moves a legacy `galaxy-cart` cookie to the new name; the cart route and `addToCart` still do.
- Creating a basket is limited to 20 per client network (an IPv4 address or an IPv6 /64) per hour. Over the limit, `POST /api/ecommerce/cart` answers HTTP 429 `{ error: 'Too many new baskets. Please try again later.' }` with `Retry-After: 3600`, and `addToCart` throws `ActionError` `TOO_MANY_REQUESTS`; neither writes a basket or cookie. Changes to an open basket are never limited. Show the message to the shopper.
- `GET /api/ecommerce/order` asks the payment provider about a pending order at most once per order every 15 seconds, and only once the order is 60 seconds old. Other requests return the stored status with the same response shape and get 200 instead of a 409 from a failed provider lookup. Without a webhook, a paid order therefore shows as pending until it is 60 seconds old, and after that for up to about 15 seconds longer than the provider reports. Checkout resume (`POST /api/ecommerce/checkout` or the `checkout` action for a basket locked by a pending order) and session release (`POST /api/ecommerce/order`) share the same slot per order, without the minimum age: while it is taken they answer HTTP 429 with `Retry-After: 15` (the action `TOO_MANY_REQUESTS`) and "The payment session was checked moments ago. Please try again in 15 seconds.", and change nothing.
- `GET` and `POST /api/ecommerce/cart` return only `{ id, items, locked }`. `GET` no longer creates a basket or sets the basket cookie; without a basket it returns `{ id: null, items: [], locked: false }`, and the `getCart` action returns `cart: null`.
- Baskets hold at most 50 lines of 1–99 units each. A new line must be a catalog product that is not archived, and its `variantId` must be a variant of that product. A product with variant groups needs one: a variant value, or a legacy group with no values. Otherwise the request gets HTTP 400, and checkout refuses such a line already in a basket with HTTP 409, so the storefront must let the shopper choose an option. Only `productId`, `variantId` and `quantity` are stored.
- `POST /api/ecommerce/discount` answers HTTP 503 `{ error: 'Checkout is disabled' }` unless `TALISMAN_COMMERCE_CHECKOUT_ENABLED` is `true`. Show a discount or gift card preview only when checkout is enabled. Its other answers changed too; see the entries below.
- Sign-in link requests accept only a bare email address; send `jane@example.com`, not `Jane <jane@example.com>`. An address with a display name or several recipients gets HTTP 400.
- A used, expired or unknown sign-in link gets HTTP 400 with the error "This sign-in link is invalid or has expired." instead of "Sign-in link is invalid or expired". A verify page that compares the old text must check the status code instead.
- Asking for a sign-in link no longer creates a shopper account; the account is created, already verified, when the link is used. Code that looks for the account after `requestCustomerEmailSignIn` finds none until then.
- `firstOrderOnly` discount codes and referral awards now require a shopper with no purchase yet: no paid, fulfilled or refunded order (admin test orders do not count) under the checkout email, the signed-in account or an account with that email. They used to look at whether a shopper account existed for the email. A shopper who signed up or asked for a sign-in link but has not bought can now use a first-order code and be referred. With `0024` applied, the database checks the same rule when an order reserves a code. Review first-order promotions that relied on the old rule.
- `purgeStaleCommerceData` also deletes the shopper accounts that earlier versions created for every sign-in link request and that nobody used: never verified, not linked to a CMS user, at least a day old, and with no order, session, open basket, credit, referral or discount use. The first scheduled run after the upgrade removes them. Its result adds `signInTokens`, `unverifiedAccounts` and `rateLimits` counts. To see the candidates before that run: `SELECT id, email, created_at FROM _ecommerce_customer_accounts WHERE email_verified_at IS NULL AND cms_user_id IS NULL`.
- The basket and gift card cookies are named `talisman-cart` and `talisman-gift-<purchase id>`. The plugin still reads the old `galaxy-*` cookies, but site code that reads a cookie by name must use the names exported from `@talisman-cms/plugin-ecommerce/cookies`.
- The **Test checkout** screen, `/admin/api/ecommerce/test-checkout` and the simulated `admin_test` payment provider need `ecommercePlugin({ adminTestCheckout: true })`. `runtimePaymentAdapters(env)` no longer returns `admin_test`, and `reconcileCommerce` cancels `admin_test` orders left pending for more than 15 minutes.
- Removed the `InventoryDO` export and `bindCommerceApi().inventory.reserve()`, which reported success without reserving stock.
- `PaymentProviderAdapter.createCheckoutSession` receives a required `currency`, the order's lowercase ISO 4217 code, and optional `shipping` (`{ label, amount, description? }`) and `tax` (`{ amount }`, the exclusive tax). A custom adapter must charge in that currency and add a shipping or tax amount above 0 to the items, less the credit, discount and gift card, or its payments never confirm. Code that calls `StripePaymentAdapter.createCheckoutSession` directly passes `currency` too. While a tax mode is set, it also needs the new optional `calculateTax`, `recordTaxTransaction` and `reverseTaxTransaction`, or checkout answers HTTP 503.
- `discountAmountForLines(code, lines, subtotal, currency)` from `/promotions` takes a required fourth argument, the store currency, and leaves that currency's minimum charge to pay instead of a fixed 50.
- Checkout accepts only officially assigned ISO 3166-1 alpha-2 country codes. The route, the `checkout` action, `createFromCart` and the admin test checkout refuse any other code, such as `UK` or `XX`, with HTTP 400 "Enter a valid country code" (the action `BAD_REQUEST`); before, the route accepted any two letters and the action and API any text. The route gives that answer instead of "Invalid checkout details", and the admin test checkout answers country and shipping refusals with 400 instead of 409. Shipping and billing countries are stored in uppercase.
- Gift cards are refused in a store whose `TALISMAN_COMMERCE_CURRENCY` is not `usd`, because their tables hold USD only: issuing and buying answer HTTP 400 "Gift cards are available only in stores that use USD", and a gift card code at checkout or in the discount preview gets the 409 code refusal. `GiftCardRefusalReason` adds `'currency'`. Balance lookups and refunds of existing cards still work.
- Amount fields in the Commerce collections and the product editor are labelled "(smallest currency unit)" instead of "(Cents)". Field names and stored values are unchanged.
- A shipped order keeps its payment status: migration `0026` moves the order status `fulfilled` to the new `fulfillmentStatus` (`unfulfilled`, `partially_fulfilled` or `fulfilled`), and a refund no longer replaces it. Code that checks `status === 'fulfilled'` reads `fulfillmentStatus`, which `listCustomerOrders` and `GET /api/ecommerce/order` return. `orders.updateStatus(id, 'fulfilled', details)` records a completing shipment and leaves `status` as it is, `fulfillCommerceOrder` returns `fulfillmentStatus` next to the payment `status`, and `listCommerceOrdersAdmin(env, options?)` takes paging options and returns one page of the queue.
- An order under an open payment dispute has the new status `disputed` and cannot ship; a lost dispute makes it `refunded`. `disputed` counts as a purchase for first-order codes, referrals and the reserved sign-in budget, and as a sale in analytics. Order and account pages should show it.
- The Stripe webhook answers an event that names none of the store's orders or gift card purchases with HTTP 200 `{ ignored: true }`, an event it cannot apply to one of them with 200 and a `reason`, a refund or dispute that arrives before its payment is recorded with 409, a refused signature with 400 and any other failure with 500. Before, every failure was answered 400.
- `GET /api/ecommerce/order` adds `paymentUnderReview` and `fulfillmentStatus`, and returns the stored status instead of HTTP 409 with the provider's text when its provider check fails. Checkout resume and `POST /api/ecommerce/order` answer a checkout parked for review with HTTP 409 and `PARKED_CHECKOUT_MESSAGE`, and the `checkout` action throws `ActionError` `CONFLICT`. `getPurchasedGiftCard` adds `paymentUnderReview`.
- `reconcileCommerce` adds a `code` to the `error` results of checkouts and tax passes and `parked: true` to the attempt that parks a row, which is then reported once and not again, and it reports order emails. It now also returns `error` results while order emails wait for a setting, when the provider refuses the sender, and when an email is given up.
- Changes that the product editor's **Options & stock** makes through the plugin's `variants` endpoint run no collection hooks registered on the variant, value, stock and variant component collections, and deleting a value or group also deletes its variant component rows.
- Gift card codes issued or re-encrypted by this release carry a key id, and a Worker from an earlier release cannot show them; re-encrypt older codes only once a rollback is no longer planned. A malformed `TALISMAN_COMMERCE_GIFT_CARD_PREVIOUS_KEYS` makes gift card purchases refuse before payment.
- Each new refund total of a gift card purchase holds the purchase for review, also after an earlier decision, and a purchase refunded in full whose cards were never spent is settled at once. Reactivating a purchased card or a replacement needs its purchase paid or resolved; suspending is always possible. `getPurchasedGiftCard` no longer shows the code of a card that was replaced.

- `STRIPE_SECRET_KEY` (or `TALISMAN_STRIPE_SECRET_KEY`) and `TALISMAN_STRIPE_WEBHOOK_SECRET` are Worker secrets read at request time. The `stripeSecretKey` and `stripeWebhooksEndpointSecret` options in `astro.config` are ignored. Until the secrets are set, syncs fail and the REST proxy and webhook endpoint return HTTP 503.

### Content and API

- Entries created outside the editor (seeds, imports, raw SQL) can now be edited and published. The first save or publish of such an entry records its stored state as revision 1 in the same batch, and the request may send `expectedRevisionId: null` or leave it out. Entries that already have revisions still need `expectedRevisionId`: a missing ID returns HTTP 428 and a stale one HTTP 409.
- Migration `0020_revision_baseline_and_globals.sql` adds a baseline revision for every entry that has none, pins the published revision of published entries, and unwraps globals stored as JSON text inside a JSON string. It only changes rows that still need it, so a rerun changes nothing.
- Published entries keep their live URL until they are published again. A slug change saved as a draft is stored as the entry's draft slug (new column `galaxy_entries.draft_slug`, migration `0021_entry_draft_slug.sql`). Admin API entry responses and `getClient().entries.create` and `update` return `slug` as the slug being edited and add `publishedSlug` (the live slug, or `null`). In draft mode `getClient().entries.findBySlug` finds an entry by its pending slug; published reads never include it.
- Entry slugs are unique within a collection. Creating an entry with, or renaming one to, another entry's slug or pending slug returns HTTP 409, and `getClient().entries.create` and `update` throw `SlugConflictError`, which `talisman-cms/client` exports. Publishing an entry whose slug another published entry already serves also returns 409. Saving with a blank slug keeps the current slug. Migration `0023_published_slug_unique.sql` adds a unique index so that only one published entry per collection holds a live slug; a publish that loses a race for it gets 409, or `SlugConflictError`. The migration fails while two published entries in a collection share a slug; the [release checklist](RELEASE.md#deployment-gate) has the query that lists them.
- Entry ids and slugs chosen by admin API clients are validated, with HTTP 400 on failure. Ids are 1–128 characters of letters, digits, `.`, `_`, `:` and `-`, start with a letter or digit, and may not be `new` or `all`. Slugs are 1–200 characters of letters, digits, `-`, `_`, `.`, `~` and `:`, with single `/` between path segments. An entry whose existing slug predates these rules can still be saved as long as the slug is unchanged.
- Entries whose id contains `:` or `.` can now be published through the Workflow binding, because Workflow instance ids are sanitised.
- Publishing through the Workflow binding checks the slug before it starts an instance, so a taken slug returns HTTP 409, or throws `SlugConflictError`, at once instead of timing out. `TalismanPublishWorkflow` does not retry a stale revision, a taken slug or a missing entry; the waiting request gets the same error as an inline publish (`RevisionConflictError`, `SlugConflictError` or `EntryNotFoundError`, all exported from `talisman-cms/client`). An instance that fails that way completes with `{ ok: false, error }` as its output. After a transition the Workflow Worker clears the entry's KV cache. The request waits up to 10 seconds (was 5); a publish or archive still running then returns HTTP 202 with the stored entry, `workflow: { status: 'pending', instanceId }` and a `message`, instead of a 500, and completes on its own. `getClient().entries` returns the same `workflow` field.
- `getClient()` publishes through the Workflow binding named by the integration's `publishing.workflowBinding` option; it always used the default name before.
- `getClient().entries.create` and `update` on native collections write the caller's data as given, so the table's own defaults still apply: no id is generated, and nothing is written to a text or other column that does not hold an integer timestamp. `create` fills a `createdAt` or `updatedAt` column only when it is an integer timestamp column (Drizzle `mode: 'timestamp'` or `'timestamp_ms'`) with no default and the caller passes no value; such a create used to fail on the `NOT NULL` column. `update` moves an integer `updatedAt` forward by at least one second, like the admin API, unless the caller passes `updatedAt`. It never writes the id column, and it skips the database update when nothing is left to write.
- Required text, textarea, select, date, color, media and single-relation fields reject blank or whitespace-only values, and required rich text fields reject empty documents. This applies on create, update and publish; publishing also validates the entry's draft against the collection's required fields.
- Validation errors for entries and globals return HTTP 400 with `{ error, fieldErrors, issues }`. `error` is a summary message instead of `Validation Error`, and `fieldErrors` lists messages by field name (a dotted path for nested fields).
- Other admin API client errors return 4xx instead of 500: invalid JSON or a body that is not a JSON object returns HTTP 400, an unknown collection, entry or revision 404, a database constraint failure 409 or 400, and a body over 2 MiB 413. Responses no longer contain SQL. Other failures return a generic HTTP 500 and are logged; messages thrown by collection hooks are still shown. The unauthenticated health check no longer returns error details.
- Globals are stored as a single JSON object. The API and `getClient().globals` always return `data` as an object, including rows and cache entries written by earlier versions. `POST /admin/api/globals/:slug` rejects data that is not a JSON object (HTTP 400), and `getClient().globals.create` and `update` throw a `TypeError` for it. Migration `0022_wrap_non_object_globals.sql` keeps stored global data that is not an object, such as a list, under a `value` key (`[1,2]` becomes `{"value":[1,2]}`).
- Only administrators can create a global. `POST /admin/api/globals/:slug` for a slug that is neither configured nor stored returns HTTP 403 for editors, who can still update configured and existing globals.
- Native collection updates accept `expectedUpdatedAt` and return HTTP 409 if the record changed since it was loaded. An update validates and writes only the columns it sends, and the response reports `updatedAt` as stored. Each update moves `updatedAt` forward by at least one second, so two saves in the same second no longer share a concurrency token and the stale one gets 409.
- An optional field left blank (`''`) by the admin form or an API client is stored as no value. Native tables get `NULL` in nullable columns, so a blank value no longer fails as "Expected number" or collides in a unique or foreign-key column; a `NOT NULL` column that is not text keeps its database default on create and its stored value on update. Optional number and select fields store `null` in entries and globals, and a blank required number reports "Required".
- Native (Drizzle-mapped) collections: the configured `fields` are the columns API clients may write. A create or update that sets another table column is refused with HTTP 400 naming the column, instead of the value being dropped silently; keys that are not table columns are ignored. Columns the admin editor sends back unchanged, the id column, `createdAt` and `updatedAt` are still accepted, and collection hooks can still set any column.
- Media records can no longer be created through `POST /admin/api/collections/media/entries` (HTTP 403); upload a file instead. A media record's `url` and `mimeType` cannot be changed after upload (HTTP 400).
- Deleting a media record deletes its R2 object and evicts this data center's cached copies. Media responses are cached for an hour (`Cache-Control: public, max-age=3600`) and revalidated with their ETag (HTTP 304), instead of for a year as immutable, under new edge-cache keys, so a deleted file stops being served everywhere within the hour. A failed upload no longer leaves an R2 object without a media record.
- Fields generated from native tables no longer mark `NOT NULL` columns that have a database default as required.
- `GET /admin/api/collections/:slug/entries` accepts `limit` (1–200) and `cursor`, and then returns `{ docs, nextCursor }`, newest first. Without `limit` it still returns the full array.
- Revision history: `GET /admin/api/collections/:slug/entries/:id/revisions` returns revision metadata without `data`. Add `?includeData=true` for full rows and `?limit=N` to shorten the list. The new `GET .../revisions/:revisionId` returns one revision with its data.
- `GET /admin/api/collections` no longer writes to D1 on each call. Collection rows are synced once per isolate, writing only missing or changed rows, and the listing takes a fixed few statements, with the row counts of all native tables from one statement. Configured globals are also created once per isolate.
- Relationship resolution queries related entries in chunks of at most 90 ids, so D1's limit of 100 bound parameters is never exceeded. It only matches entries in the target collection, leaves ids of collections that only administrators may read unresolved, and uses the deployed config's fields.
- Removed `getClient().tasks.enqueueImageProcessing` and the `QUEUE` entry of `TalismanEnv`. There was never a queue consumer.
- New `talisman-cms/richtext` export: `renderRichText(value, { headingOffset })` renders stored Tiptap JSON as safe HTML. It escapes all text, keeps only the editor's nodes and marks, and keeps only relative, http(s), `mailto` and `tel` links. A string value is shown as plain text. It also exports `richTextToPlainText`, `safeRichTextHref` and `escapeHtml`, and the core README has a section on rendering rich text.
- The ecommerce demo seed (`seeds/ecommerce-demo.sql`) stores post content as Tiptap JSON, so `renderRichText` shows it as formatted text instead of raw `<p>` tags. To fix posts seeded before this release, rerun `db:seed:ecommerce:local`. Opening and saving a post in the admin does not convert it: an HTML string becomes Tiptap JSON only when you edit the rich text field itself, save and publish.
- The KV cache is best-effort: a failed KV read or write falls through to D1 instead of failing the request. `getClient` accepts the request's execution context so cache fills finish after the response (inside the Worker it is otherwise taken from `cloudflare:workers`). A fill is dropped when the content it read was changed or hard-deleted while the read was in flight, so stale content is not cached for the TTL.
- `talisman-cms/client` exports `invalidateEntryCache(env, collectionSlug, ids?)`, which takes one id or a list, for server code that writes D1 directly: it drops the KV copies of the collection's lists and of those entries once the write has committed.
- A native update keeps moving `updatedAt` forward from a stored value that runs ahead of the clock, which bursts of plugin stock writes can cause, so a concurrency token never returns to a value an editor may still hold. Only a value more than a year ahead, such as a seed that wrote milliseconds, is reset to now; before, anything more than five minutes ahead was.

### Admin

- Entry editor: after the first save of a new entry, Save and Publish work without reloading (no more 428 "expectedRevisionId is required"), and publishing a new entry and then saving no longer returns 409.
- Entry editor: when a save is refused because the entry or record changed elsewhere (409), your edits stay in the form. You can load the latest version, copy your changes, or put back only the fields you changed. Other fields keep their latest values, so another editor's changes and stock reserved by checkouts are not overwritten. A refused Publish, Archive or Restore with no unsaved edits loads the latest version and asks you to retry.
- Entry editor: after a save conflict and **Load latest version**, the changes held in the conflict panel still count as unsaved. The **Unsaved changes** badge stays, leaving the page or closing or reloading the tab asks first, and **Dismiss**, Save, Publish, Archive and revision Restore ask before discarding them. **Load latest version** also keeps edits made after the conflict appeared, in the form or in raw JSON, and refuses to replace raw JSON that does not parse.
- Entry editor: rich text fields no longer count as edited when you only open, click into or tab through them, or when Tiptap reformats the stored content on load. The **Unsaved changes** badge and leave prompt stay quiet, and Publish no longer saves an extra draft first. After a save conflict the panel lists only the fields you actually edited, so **Put my changes back** no longer overwrites another editor's rich text that you only clicked into.
- Entry editor: rich text fields clear when the loaded version has no content, instead of showing the previous text.
- Entry editor: saving a native record, such as a product, sends the `updatedAt` it loaded, so stale saves are refused. Stock and inventory quantities are sent only when you change them, in the product form and in the options & stock section, so editing a product no longer overwrites stock that checkout has reserved. Native records no longer request revision history.
- Entry editor: optional number, select and relation fields left blank are saved as `null`, or left out of a new native record so the column default applies, instead of `''`. This stops "Expected number" errors, "A value is required" for a cleared **Inventory Quantity** on a new product, and 409s from blank unique or foreign-key values, such as a variant group saved with no option definition. The variant editor now clears SKU, image, price override and option definition when they are emptied.
- Entry editor: validation errors show readable messages (never "[object Object]") under each field, in the block inspector, and in a summary that names the field. Blocks with invalid fields are marked in the page outline. Server, network and expired-session errors are explained in plain words.
- Entry editor: warns before leaving or reloading with unsaved changes, and asks before restoring a revision over unsaved edits. Edits made in the raw JSON view are kept when switching back to the form.
- Entry editor: Publish and Archive no longer add an extra draft revision when there are no unsaved changes.
- Entry editor: media fields upload to and browse the media library under the configured admin path, and Browse loads the library once instead of sending requests in a loop.
- Collection lists load 50 entries at a time, with a **Load more** button. The revision history loads only the metadata of the latest 50 revisions.
- The media library and the media picker show the newest uploads first and load 60 and 48 items at a time, with **Load more**.
- Faster admin loading: related records load in parallel, 200 rows per request, and the collections list is reused for a minute. Saving no longer reloads the whole editor, and the variant editor reloads only its own tables.
- A published entry with a saved slug change shows its live address and the pending rename, in the collection list and under the editor's slug field, until the rename is published.
- Entry editor: only a stale edit opens the conflict panel. A slug another entry uses is reported at the slug field, and other refused saves, such as a unique-value or foreign-key clash, show the server's message.
- Entry editor: when a publish or archive is answered with HTTP 202 because its Workflow is still running, the editor shows the server's message and keeps Save, Publish, Archive and Restore disabled while it checks the entry, waiting 3, 6 and then 10 seconds between checks. It then reports that the entry is published or archived, or that it changed some other way, or offers a **Reload entry** button. A second click therefore no longer starts another Workflow instance.
- Entry editor: those checks only fetch the entry to see whether it has changed; they do not reload it into the form, so text typed during the server's wait or while the status shows is kept. When the transition lands, the entry is reloaded only if the form has no unsaved changes, and if the user starts typing during that reload, the form is left as it is. In both cases the notice says the unsaved changes are still in the form.
- Entry editor: the live preview broadcast for a publish or archive that is still running is sent once the transition has happened, not when the 202 arrives.
- `talisman-cms/ui/lib/entry-save.ts` adds `readPendingTransition`, `hasEntryMovedOn`, `describeSettledTransition`, `waitForPendingTransition` and `PENDING_TRANSITION_CHECK_DELAYS_MS` for a publish or archive that is still pending.
- Page builder: moving or removing a block no longer opens the Inspector.
- Accessibility: form fields and pickers have linked labels and linked error messages, and rich text toolbar buttons have names and an on/off state. The page builder Inspector is a modal dialog: focus moves into it, Tab stays inside, Escape closes it and focus returns. Collection and entry rows open from the keyboard, the **Users** confirm and reset forms receive focus, and the media upload can be reached by keyboard.
- Globals: saving a global with configured fields keeps the saved values in the form, so a second save no longer undoes the first, and the **Updated** time refreshes. Validation errors are shown next to each field and in a summary under the form.
- Globals: the raw JSON editor for globals without configured fields keeps what you type, saves exactly that document, keeps the **Saved** notice visible, and refuses JSON that is not an object with a clear message.
- Editors no longer see screens they cannot use: **New Global**, **Users**, **Ask Analytics** and the admin-only commerce tools. Opening one directly explains that admin access is required. The sidebar instead links editors to the commerce content collections they can edit.
- With hybrid auth, **Sign out** for Cloudflare SSO admins also ends the Cloudflare Access session. The button and the **Account** page say so, and a failed sign-out is reported. With Access auth, the "not authorized" screen offers a link to sign out of Cloudflare Access.
- **Users** reports a successful role change or access revocation as successful, shows server warnings (for example when existing sessions could not be ended), and refreshes the list after a failed action. It can re-enable a disabled account that no longer has CMS access, such as a disabled shopper account.
- The admin SPA's browser bundle gets a client-safe copy of `virtual:talisman-cms/config`. It leaves out `runtimeHooks` and their `args` and the `publishing` binding, and drops keys or values that look like secrets, with a build warning. Server code still receives the full configuration.
- Dev Toolbar: links follow the configured `adminPath`, and it lists your collections, globals and UI libraries and checks the `DB` binding live. The hard-coded collection and plugin lists, the "D1 + KV Active" status and the version label are removed.
- Commerce prices in the admin are scaled and formatted by the store currency's minor units instead of divided by 100. The admin page renders `<meta name="talisman-commerce-currency">` from `TALISMAN_COMMERCE_CURRENCY` (USD when it is not a three-letter code), which the product editor's preview and relation labels read through the new `readCommerceCurrency()` in `talisman-cms/ui/commerce-currency.ts`, and the commerce plugin's screens read too. `talisman-cms/ui/lib/commerce-models.ts` exports `formatMoney(amount, currency)`, and `describeCommerceEntry` and `getRelationOptionLabel` take an optional `currency`; without it they leave prices out. Price fields are labelled "(smallest currency unit)" instead of "(Cents)".
- Product editor: **Options & stock** saves a value with its stock, deletes a value, and deletes a group with its values, stock and variant component rows, each as one request to the ecommerce plugin's `variants` endpoint, so a failure leaves nothing half saved and a retry creates no duplicate. After a refusal that wrote nothing the edits stay; after a stale token, a missing row or an unknown outcome the editor loads the saved rows and says so, and when they cannot be loaded it keeps the edits, offers **Load latest options and stock** and waits for them before creating a value. A refused read no longer empties the editor: `fetchAllEntries` and `fetchEntriesBySlug` in `talisman-cms/ui/lib/admin-api.ts` take `strict`, which makes a refused first page throw instead of reading as empty.
- The Commerce workspace lists the read-only **Gift Card Reviews** collection with the other gift card records.

### Authentication and users

- Sign-in rate limits are kept per client, keyed on `CF-Connecting-IP`, instead of in one shared bucket; `X-Forwarded-For` is ignored. The Cloudflare SSO sign-in is not subject to other clients' limits, so failed password attempts can no longer lock the SSO admin out, and it no longer rewrites the admin's stored credential on every sign-in.
- Password sign-in no longer reveals which emails belong to admins or shoppers. In hybrid mode an admin or shopper email gets the same HTTP 401 "Invalid email or password" as a wrong password, instead of a 403. With plain `LocalAuthAdapter`, a `customer` account that still has a password gets that 401 and no session. A disabled account gets the same 401 whether or not its password is right, instead of a 403 that confirmed the password.
- Admin actions reject a non-string `userId` or `role` with HTTP 400.
- CMS sessions end 7 days after sign-in, even if they are used continuously. The 12-hour inactivity timeout still applies.
- Plugin endpoints without `public: true` (served under `<adminPath>/api/`), and plugin pages under the admin path, now require a CMS session by default. API routes answer HTTP 401 JSON and pages redirect to the admin sign-in; a page opts out with `public: true`, which the `Plugin` type's `routes` items now declare. Prerendering an admin-path page that needs a session is a configuration error.
- `DevAuthAdapter` now fails `astro build` and `astro preview`, and refuses a dev server exposed with `--host` or `server.host`. It only signs requests in under the Vite dev server (`import.meta.env.DEV`) on a loopback host, never in a built Worker.
- First-admin setup with an email that already belongs to a shopper, or to any other account, returns HTTP 409 with a clear message instead of failing with 500.
- Fixed: changing a user's role (including **Revoke CMS access** in hybrid mode), resetting a password or disabling a user no longer returns a server error after the change is saved, and the user's existing CMS sessions are ended as intended. If ending them fails, the auth API returns 200 with a `warning` field, because the change itself was saved. Role changes and disabling still take effect immediately, and the warnings after **Disable** and **Revoke CMS access** no longer ask the admin to repeat the action.
- Enabling a disabled account, or granting a CMS role to an account without one (**Add editor** for a shopper, or `admin/set-role` in local mode), ends that account's existing sessions first. If they cannot be ended, the request returns HTTP 503 and nothing changes.
- A disabled account that lost CMS access keeps the `customer` role and can be re-enabled with **Enable** (`admin/unban-user`) without gaining CMS access; it gets none until an admin grants a role. **Add editor** on such an account while it is still disabled returns HTTP 409 and asks you to enable it first.

### Settings

- Worker settings and the default Workflow binding are renamed from `GALAXY_*` to `TALISMAN_*`, for example `TALISMAN_AUTH_SECRET`, `TALISMAN_ACCESS_*`, `TALISMAN_COMMERCE_*` and `TALISMAN_PUBLISH_WORKFLOW`. A `GALAXY_*` name is still read when its `TALISMAN_*` name is missing or blank, and the Worker logs a one-time deprecation warning. To migrate, rename each key and keep its value.
- New `talisman-cms/env` export for plugins and sites: `readSetting(env, name)` and `readBinding(env, name)` read `TALISMAN_<name>` and fall back to `GALAXY_<name>`.
- Setting values are trimmed, and a blank value counts as unset. A number or `true`/`false` in `wrangler.toml` `[vars]` is read as text, so `TALISMAN_COMMERCE_EMAIL_DAILY_LIMIT = 500` works; a list or table is ignored, with a one-time warning in the Worker log.
- The core README has a settings reference covering every `TALISMAN_*` setting, including `TALISMAN_COMMERCE_LOCAL_STRIPE_*`, and the Stripe and analytics settings.
- Live preview: the admin now broadcasts `TALISMAN_ENTRY_SAVED`. `LivePreview` accepts both the `TALISMAN_ENTRY_*` and the old `GALAXY_ENTRY_*` message types; custom preview listeners should switch to `TALISMAN_ENTRY_*`.
- The `galaxy_` database table prefix is internal and permanent; no migration is needed.

- New `talisman-cms/email` export, safe to import outside the Worker. It provides the `EmailProvider` interface, `EmailDeliveryError` (with a `code` and `retryable`), `sendEmail`, which blocks header injection and adds `Auto-Submitted: auto-generated` and `X-Talisman-Email` headers, `parseAddress`, the Cloudflare Email Service `send_email` provider, a console provider that runs only on localhost, `renderTransactionalEmail`, `escapeHtml` and `customEmail()`.
- New Worker-only `talisman-cms/email/runtime` export with `getEmailProvider(env)` and `sendConfiguredEmail(env, message)`. `TALISMAN_EMAIL_PROVIDER` chooses the provider (`cloudflare`, `console`, `custom` or `none`), configured by `TALISMAN_EMAIL_FROM`, `TALISMAN_EMAIL_REPLY_TO`, `TALISMAN_PUBLIC_ORIGIN` and `TALISMAN_EMAIL_BINDING` (default `EMAIL`). With the setting unset, a registered provider is used, then a binding named `EMAIL`.
- New `email` integration option registers a custom email provider: `talismanCms({ email: customEmail({ moduleId, exportName, args }) })` is validated when the config loads and served to the Worker as `virtual:talisman-cms/email`.

### Ecommerce plugin

- Shopper sign-in email goes through the Talisman CMS email provider, by default a Cloudflare Email Service `[[send_email]]` binding named `EMAIL`. Built-in Resend support and `RESEND_API_KEY` are removed; register Resend or another HTTP email API as a custom provider.
- The sign-in sender falls back from `TALISMAN_COMMERCE_EMAIL_FROM` to `TALISMAN_EMAIL_FROM`, and the public origin from `TALISMAN_COMMERCE_PUBLIC_ORIGIN` to `TALISMAN_PUBLIC_ORIGIN`. A trailing slash on the origin is accepted.
- Sign-in links carry the token in the URL fragment (`/account/verify#token=…`), so it never reaches the server or its logs. Use the new `readCustomerSignInToken()` from `@talisman-cms/plugin-ecommerce/browser`, which also accepts older `?token=` links and removes the token from the address bar.
- Asking for a shopper sign-in link no longer creates an account. The link stores only the token's hash and the address it was sent to, in the new `_ecommerce_sign_in_tokens` table (migration `0024_shopper_sign_in_tokens.sql`), and the account is created, already verified, or linked when the link is used. Unexpired links sent before the upgrade keep working.
- First-order discount codes and referral awards depend on purchase history (paid, fulfilled or refunded orders, not admin test orders) instead of on whether an account exists. Shoppers who signed up or asked for a link before their first purchase keep both, signed-in shoppers with no purchases can now be referred, and when two checkouts by the same shopper overlap, only the first one paid earns the award.
- New sign-in link preview: `POST /api/ecommerce/account` with `{ token, preview: true }` returns the masked address the link was sent to, such as `{ email: 'j•••@example.com' }`, without using the link. The browser helper is `previewCustomerSignIn(token)`. Previews are limited to 20 per hour per source IP (IPv6 per /64), apart from sign-in requests, and answer HTTP 429 beyond that. A used, expired or unknown link answers HTTP 400 "This sign-in link is invalid or has expired." to previews and sign-ins (it was "Sign-in link is invalid or expired").
- Sign-in link requests accept only a bare email address. An address with a display name or several recipients gets HTTP 400, and the link is always sent to exactly the lowercased address.
- The per-IP limits and the daily cap on sign-in emails are kept in the plugin's own `_ecommerce_rate_limits` table, so better-auth's cleanup of its own rate-limit table no longer deletes them.
- When a sign-in email cannot be sent, the account API returns HTTP 503 with a readable message instead of 400. Logs include only the provider's error codes, never addresses, links or tokens. Suppressed recipients get the normal accepted response.
- New store-wide daily limit on sign-in emails, `TALISMAN_COMMERCE_EMAIL_DAILY_LIMIT` (default 200). Part of it, `TALISMAN_COMMERCE_EMAIL_RESERVED_DAILY` (default a quarter of the limit, rounded down, so 50 of 200; a value that is not a whole number from 0 to the limit minus 1 means the default), is kept for addresses with a verified shopper account or a purchased order (paid, fulfilled, partially refunded or refunded; admin test orders do not count). The rest, the general pool, serves every address. Once the general pool is spent, every request answers HTTP 200 `{ accepted: true, limited: true }`; only those existing customers are sent a link, from the reserve, and each address at most twice per 24 hours. The lookup and the send from the reserve run after the response through `waitUntil`, so the answer takes the same time for every address, and a failed send there is logged, never returned. Each limited request logs `[commerce] Daily sign-in email limit reached` with `{ pool: 'general' }`. `requestCustomerEmailSignIn` returns `{ limited }` and no longer throws `CustomerEmailLimitError`. The per-IP sign-in limit counts IPv6 addresses per /64 prefix.
- The per-address limit of three sign-in requests per ten minutes is also kept as an atomic counter in `_ecommerce_rate_limits`, next to the count of recent links, so parallel requests for one address share it. Counters that concern an address hold only a SHA-256 hash of the normalized address.
- Optional Cloudflare Turnstile check for email sign-in. `TALISMAN_COMMERCE_TURNSTILE_SITE_KEY` (public) and the secret `TALISMAN_COMMERCE_TURNSTILE_SECRET_KEY` are set together; blank counts as unset. With the secret set, the account route verifies the request's `turnstileToken` with Cloudflare siteverify (secret, token and `remoteip` from `CF-Connecting-IP`, 5-second timeout, failing closed) before any counter, link or email. It accepts only `success: true`; a hostname siteverify reports must equal the host of `TALISMAN_PUBLIC_ORIGIN` (or `TALISMAN_COMMERCE_PUBLIC_ORIGIN`), and a reported action must be `shopper-sign-in`. Cloudflare's published test secret keys skip those two comparisons and are accepted only when the public origin is a local development host (`localhost`, `127.0.0.1`, `[::1]`, `*.localhost` or `*.test`). A missing or failed check answers HTTP 403 "The security check failed. Please try again." and logs `[commerce] Email sign-in bot check refused` with a code (`missing_token`, `rejected`, `unavailable`, `hostname_mismatch`, `action_mismatch` or `test_key`) and Cloudflare's error codes. A secret without a site key answers 503 "Email sign-in is unavailable" and logs `turnstile_site_key_missing`. The checks run in this order: same origin, email configuration (503), address format (400), Turnstile (403), then the counters and the send. Link previews and link use need no token.
- New exports from `@talisman-cms/plugin-ecommerce/accounts`: `shopperSignInBotCheck(env)`, which returns `{ provider: 'turnstile', siteKey, action }` when both keys are set and otherwise `null`, so the storefront knows whether to render the widget; `normalizeShopperEmail(email)`; and the `CustomerEmailSignInOptions` type. The browser helper `requestCustomerEmailSignIn(email, { turnstileToken })` sends the token.
- `GET` and `POST /api/ecommerce/cart` return only `{ id, items, locked }`. The basket session token, account id and payment session id are no longer in the response.
- `GET /api/ecommerce/cart` no longer creates a basket or sets the basket cookie. Without a basket it returns `{ id: null, items: [], locked: false }`, and the first `POST` that adds items creates the basket. Cross-origin `POST`s no longer set the cookie either.
- The `getCart` and `clearCart` actions no longer create a basket either; `getCart` returns `cart: null` when there is none. `addToCart` validates the product before creating a basket and limits its input.
- `POST /api/ecommerce/cart` rejects bodies over 64 KiB (413), non-JSON bodies and a non-array `items` (400) before creating a basket. Posting an empty item list with no basket writes nothing.
- Baskets hold at most 50 lines (was 100) of 1–99 units each, exported as `CART_MAX_LINES` and `CART_MAX_LINE_QUANTITY`. A new line must be a catalog product that is not archived, and its variant must belong to that product; otherwise the request gets HTTP 400. Only `productId`, `variantId` and `quantity` are stored, and a rejected request creates no basket or cookie. New `carts.validateItems` checks an item list without writing.
- A product with variant groups can only be added to the basket or bought as one of its variants: a variant value, or a legacy variant group with no values. The cart API answers HTTP 400 `Cart items must choose one of the variants of <product id>` to a line without a variant or naming the group itself, and quote and checkout refuse such a line already in a basket with `Select an option for <product name>` (HTTP 409 from the checkout route).
- The checkout route and action, and the discount preview route (`POST /api/ecommerce/discount`), check `TALISMAN_COMMERCE_CHECKOUT_ENABLED` before anything else. While it is off, both routes answer HTTP 503 "Checkout is disabled", even to a request without a basket cookie or a cross-site or malformed one; the preview then reads no basket, account, discount code or gift card, and the action no longer sets a basket cookie.
- Discount preview (`POST /api/ecommerce/discount`): after the checkout, same-origin and body checks, each preview counts against a code-check budget of 30 per client network (an IPv4 address or an IPv6 /64, from `CF-Connecting-IP`) and 10 per basket per hour, in fixed one-hour windows in `_ecommerce_rate_limits` (keys `code-check:<hash>` and `code-check-basket:<basket id>`). Every checkout that carries a discount or gift card code, through the route or the action, counts against the same budget; a checkout without a code does not. Over either limit the answer is HTTP 429 "Too many code checks. Please try again later." Without a client IP, as in local development, only the basket limit applies. The limits are code constants, not settings.
- Every refusal of an entered discount or gift card code, in the preview and at checkout, answers HTTP 409 `{ error: 'This code is not valid for this order.', field: 'code' | 'giftCardCode' }`; the checkout action throws `ActionError` `CONFLICT` with that message. At checkout, a discount code over 32 characters or a gift card code over 37 fails input validation first (HTTP 400 "Invalid checkout details" from the route, an input validation error from the action). The reason stays on the server in the typed errors `DiscountCodeRefusal` and `GiftCardRefusal`, which carry a reason code. Basket problems keep their own answers: 404 "Basket not found" without a basket cookie, and 409 "Basket is not available for discounts" for a missing, empty or locked basket. New exports: `DiscountCodeRefusal`, `DiscountRefusalReason`, `CODE_REFUSAL_MESSAGE` and `codeRefusalBody` from `/promotions`, and `GiftCardRefusal` and `GiftCardRefusalReason` from `/gift-cards`. `evaluateDiscountCode` and `evaluateGiftCard` keep their detailed messages for other callers, and `evaluateDiscountCode` accepts `checkShopperHistory` (default `true`).
- The discount preview decides only from the basket and the signed-in shopper's own account. It accepts `customerEmail` in any form and ignores it. First-order and per-customer rules are checked in the preview only for a signed-in shopper, against that account's id and email; for a guest they are checked at checkout with the checkout email. The preview links a browser basket to a signed-in account as the cart route does, never creates a basket, and accepts codes up to 200 characters.
- Basket creation is limited per client network: at most 20 new baskets per IPv4 address or IPv6 /64 per hour (`NEW_BASKETS_PER_NETWORK_PER_HOUR`), shared by `POST /api/ecommerce/cart` and the `addToCart` action and kept in `_ecommerce_rate_limits` under `basket-create:<hash>`. Only a request that creates a basket counts, after its items pass validation. Over the limit the route answers HTTP 429 "Too many new baskets. Please try again later." with `Retry-After: 3600`, the action throws `ActionError` `TOO_MANY_REQUESTS`, and neither writes a basket row or cookie. Changes to an open basket, reads and emptying a basket that does not exist are never counted. A request without a client IP is not limited.
- The checkout route and the `checkout` action only use an existing open basket, linking a browser basket to a signed-in account as the cart route does, and never create a basket or a basket cookie. The checkout-disabled gate still comes first.
- Order status (`GET /api/ecommerce/order`): for a pending order whose provider is a configured payment adapter, the route asks the provider for the checkout session only once the order is 60 seconds old, and at most once per order every 15 seconds. The slot is taken atomically in `_ecommerce_rate_limits` under `order-status:<order id>`. Any other request returns the stored status with `Cache-Control: no-store` and the same shape. The webhook normally settles an order within that time, and scheduled or admin reconciliation (`reconcileCommerce`), gift-card orders and simulated `admin_test` orders are not limited by it. Checkout resume and session release share the slot, without the minimum age, through `resumeFromCart(cartId, { limitProviderChecks: true })` and `cancel(id, { limitProviderChecks: true })`, which the checkout route and action and the release route pass; a limited resume returns `providerCheckLimited: true`, and a limited release throws `ProviderCheckLimitedError` (exported with `PROVIDER_CHECK_RETRY_MESSAGE` from `@talisman-cms/plugin-ecommerce/api`). Without the option these methods ask the provider on every call. Keep the Stripe webhook and the scheduled reconciliation configured.
- Referral rules. Referrals are off unless a saved policy enables them or, with nothing saved, `TALISMAN_COMMERCE_REFERRALS_ENABLED` is `true` (a TOML boolean `true` also counts). The reward may be at most half the minimum first order; the admin can save settings with the switch off whatever the terms, and enabling with a larger reward is refused with a plain message. The admin **Promotions** screen shows whether the saved settings or the Worker settings apply, any terms error, and the hold, cap and period as read-only values.
- A referral is attributed at checkout only when the subtotal less the promotion discount reaches the minimum. The buyer must have no earlier purchase and must not be the referrer. Addresses are compared exactly and in canonical form: lowercased and trimmed, a `+suffix` dropped on every domain, and for `gmail.com` and `googlemail.com` dots dropped and the domain set to `gmail.com`. The checkout email, the signed-in account's email and the payment provider's email are compared with the referrer's, and with earlier purchasers, at checkout and again at payment. `canonicalEmail` is exported from `/referrals`, with `referralTermsError`, `referralNetAmount`, `referralOrderQualifies`, `referralReversalStatements`, `reverseReferralForOrder`, the defaults `REFERRAL_HOLD_DAYS`, `REFERRAL_MAX_PER_PERIOD` and `REFERRAL_PERIOD_DAYS`, and the types `ReferralPolicy`, `ReferralDashboard` and `ReferralReleaseResult`.
- Payment records the referral as pending only while the referrer has fewer than `TALISMAN_COMMERCE_REFERRAL_MAX_PER_PERIOD` (default 10) approved referrals created within `TALISMAN_COMMERCE_REFERRAL_PERIOD_DAYS` (default 30), checked atomically. Referrer accounts whose addresses share a canonical form share one cap. A voided referral no longer counts.
- New `releaseReferralAwards(options, { now, limit })` in `/referrals`, which `reconcileCommerce` calls with the same limit (default 10). An award is released once `TALISMAN_COMMERCE_REFERRAL_HOLD_DAYS` (default 30) have passed since payment, the order still qualifies and the payment provider reports no dispute, whether or not new referrals are enabled. Release credits `referral_award` to the referrer and `welcome_award` to the referred shopper, once each. An open dispute keeps the award pending, and so does a Stripe order when no adapter can report disputes.
- An order keeps its referral while it is paid, fulfilled or partially refunded and its net amount (subtotal less the promotion discount, provider refunds and gift card refunds) reaches both twice the award's reward, which is fixed at checkout, and the current minimum order, counted only up to what the order qualified with at checkout (its subtotal less the discount). A provider refund (full or partial, `charge.refunded`) or a gift card tender refund (`refundGiftCardTender`) that takes the order below that amount voids the referral and reverses released awards once (`referral_reversal`, `welcome_reversal`), in the same batch as the refund. A refund that leaves enough paid changes nothing, and changed terms alone never void or reverse an award. Gift-card-only orders are never attributed, so `refundGiftCardOnlyOrder` does not touch referrals.
- The Stripe webhook handles `charge.dispute.closed`. A lost dispute of a recorded payment voids the order's referral and reverses released awards, as part of the full refund that the dispute entries below describe, and the event is answered `{ success: true, event, orderId, status }`. `PaymentProviderAdapter` adds an optional `getDisputeStatus(paymentIntentId)` returning `'none'`, `'open'` or `'lost'`, which `StripePaymentAdapter` implements.
- Stripe checkout coupons are single-use. Each discounted Stripe checkout (promotion, store credit or gift card applied) creates its coupon with the id `<order id>_discount`, `max_redemptions: 1` and `redeem_by` at the session's `expires_at`. Checkout Sessions for plugin orders now last 31 minutes instead of 30, because Stripe needs at least 30 minutes after creation and the coupon is created first. The coupon is deleted when its order is cancelled (by the `checkout.session.expired` webhook, by reconciliation, or by a shopper or admin cancel), when a session expires for an order that was never recorded, and when checkout fails after the session was requested, even if expiring that session fails. Deletion is best effort: a failure logs `[commerce] Checkout discount could not be discarded` with the provider, error name and code only, and never blocks releasing stock, credit, gift card or promotion reservations. `PaymentProviderAdapter` adds an optional `discardCheckoutDiscount(orderId)`, and `@talisman-cms/plugin-ecommerce/adapters/stripe` exports `checkoutCouponId(orderId)`. Coupons created by earlier versions have random ids and are not deleted automatically.
- New internal `src/rate-limits.ts` holds the shared limiter (`sha256Hex`, `rateLimitSource`, `countRequest`, `peekRequestCount`, `clientOverLimit`, `claimInterval`). Its windows must be 24 hours or less, because the retention purge deletes counters whose window started more than a day ago, and `countRequest` throws a `RangeError` otherwise.
- New `ecommercePlugin({ adminTestCheckout })` option, default `false`. ### Stripe plugin

- Stripe secrets are read from the Worker at request time and never compiled into the server bundle: `STRIPE_SECRET_KEY` (or `TALISMAN_STRIPE_SECRET_KEY`, which takes precedence) and `TALISMAN_STRIPE_WEBHOOK_SECRET`. The `stripeSecretKey` and `stripeWebhooksEndpointSecret` options in `astro.config` are ignored with a warning.
- Syncs, the REST proxy and the webhook endpoint refuse to run until their secret is set. Saves that would call Stripe fail with a clear error, and the REST proxy and webhook endpoint return HTTP 503.
- The public `/api/stripe/webhooks` endpoint is added only when `webhooksModule` is set or `webhookEndpoint: true`. Signatures are verified with that endpoint's own signing secret.
- Stripe IDs are taken only from the stored record. `stripeID` and `skipSync` values sent by the admin form or API clients are ignored, and the plugin no longer adds hidden `stripeID`/`skipSync` fields to synced collections. The new `stripeIdField` option (default `stripeID`) names the field or column that holds the ID.
- Collections with a native table must have a column for the Stripe ID, and saves are refused without one. Previously the ID was dropped and every save created another Stripe resource.
- Deleting a record linked to Stripe requires the CMS admin role and a configured key. Linked products and prices are archived in Stripe (`active: false`) instead of deleted; customers are still deleted.
- The `./routes/*` export resolves to built files in `dist/`, and the package no longer ships or imports TypeScript source. Stripe calls use the fetch HTTP client, so they work in Workers.
- Adds a README covering installation, configuration, required secrets, what is synced, and security notes.

### Analytics plugin

- Sales, refunds and top products leave out Stripe test-mode orders only when `TALISMAN_COMMERCE_STRIPE_MODE` is `live`: orders whose Checkout Session id starts with `cs_test_`, and gift-card-only orders paid with a gift card bought in test mode. - The Commerce analytics response and the Ask Analytics report's `commerce` data include `stripeMode` (`live` or `test`). The Commerce toolbar and the Ask report notes say whether Stripe test-mode orders are excluded or included.
- Refunds count on the date they were issued when the database has a `_ecommerce_provider_refunds` table, one row per provider refund. Net sales are then gross sales less the refunds issued in the period, and an order's provider refunds never count for more than its provider refund total, so a refund recorded twice is not counted twice. Migration `0028` creates the table, and the ecommerce plugin records there each rise in an order's refund total. Refunds recorded before it, and payments taken back by a lost dispute, have no date of their own and count on the payment date of the order, and the report notes it. Both screens say which rule applies.
- An order under an open payment dispute counts as a sale until the dispute is lost, which makes it refunded.
- Average order is gross sales per order, each Refunds figure shows how many orders were refunded, and the daily chart marks days where refunds exceed sales.
- Ask Analytics compares like with like. Today is compared with yesterday up to the same time, and this month with the same days of last month, or with all of last month once this month is longer. Yesterday, last month and the last 7 or 30 days are compared with the equal span before them. The summary names the exact window it compares with, and report date ranges show exact UTC times whenever a boundary is not at midnight.
- Ask Analytics: a Refunds report is summarized and compared by refunds and refunded orders, not net sales, and a Top products report names the best seller in each currency. Refund comparisons say what they compare: "USD refunds issued rose …" once refund dates are recorded, and until then the refunds on the orders paid in each window, as in "Refunds on USD orders paid in this period fell 90% compared with orders paid …". The refund metrics label the previous value "issued then" or "on orders paid then" to match.
- Ask Analytics: the example question "Did refunds increase compared with the previous 30 days?" is replaced by "Show refunds for the last 30 days".
- Amounts are formatted by each currency's minor units instead of divided by 100, so JPY shows no decimals and KWD three, on the Commerce screen, in its daily chart's tooltips and in Ask Analytics.
- Gross sales leave out the shipping and tax added to the price, and a refund counts against sales only for the items' share of it: the refund × gross ÷ (gross + shipping + exclusive tax), in integer arithmetic, rounded half up and never more than the gross. A full refund counts the whole gross. Orders without shipping or exclusive tax, including every order from before migration `0025`, keep their numbers. By refund date, each dated refund counts for the share of the order's refunds up to and including it less the share of those before it, so the parts add up to the order's share; a refund whose items' share is 0 no longer counts as a refunded order. The Commerce screen's footnote and a new Ask report note state the rule, and `CommerceOverview.currencies` documents `grossSales`, `refunds`, `netSales` and `charged`. The commerce queries read the order columns that migration `0025` adds.

### Packaging

- `talisman-cms` declares `astro`, `drizzle-orm`, `react` and `react-dom` as peer dependencies and no longer bundles drizzle-orm. Plugins declare `talisman-cms` (`^0.1.0` when packed) and `astro` as peers, plus React or drizzle-orm where they use them. React is deduplicated for the admin SPA, which fixes a blank `/admin` under `astro dev` with installed packages.
- Packages are ESM-only, and each build clears `dist/` first. Manifests declare `repository`, `homepage`, `bugs` and Node `>=22.12.0` in `engines`.
- Every published package includes a `NOTICE` file with third-party attributions (daisyUI, shadcn/ui), a copy of the repository's root `NOTICE`. `pnpm release:check:archives` checks that each packed copy matches.
- Removed the `db:generate` script, `drizzle.config.ts` and the stale drizzle-kit snapshots. CMS migrations are hand-written SQL, and the published `drizzle/meta` folder holds only `_journal.json`. A new migration test applies the whole chain to an empty database and to one holding data from earlier releases.
- Publishing requires pnpm: `prepublishOnly` stops `npm publish`, which would ship unresolved `workspace:` ranges and no license text. Each package builds in `prepack`, so `pnpm pack` and `pnpm publish` always pack a fresh build.
- `pnpm release:publish` publishes every package with pnpm; run it with `--dry-run` first. The rebuild in `prepack` can reorder members in some `.d.ts` files, which stopped the next publish at pnpm's clean-tree check. The script and `scripts/check-dist-drift.mjs` now list those files and put them back, and the script fails when the build it packed differs from the committed `dist/`. Only a change of order within one union or one `{ … }` block is ignored; a union member or property that moves to another declaration, or any other change, fails the check.

### Upgrading

The release build is validated with Astro 7. To upgrade a site built on the pre-release source:

1. Make the code and configuration changes that the [breaking changes](#breaking-changes) call for.
2. Back up the D1 database, run the pre-checks, and apply the new migrations, `0019_shared_customer_identity.sql` through `0030_commerce_order_emails.sql`, as the [release checklist](RELEASE.md#deployment-gate) describes. The migrations folder also creates the ecommerce plugin's tables, so apply every migration a version ships even if the site does not use that plugin.
3. Add the `TALISMAN_*` settings and secrets with the values of their `GALAXY_*` names, the `EMAIL` binding if the site sends shopper sign-in email, and the Stripe secrets if it uses the Stripe plugin. For the ecommerce plugin, decide whether referrals run (check the saved policy with the read-only query under [Deployment and settings](#deployment-and-settings)), set both Turnstile keys or neither, add `charge.dispute.created` and `charge.dispute.closed` to the Stripe webhook's events, and configure email and the store details for order emails. A store that sells in a currency other than USD, limits its delivery countries, or charges shipping or tax sets the new store settings before it enables checkout, as the ecommerce README describes, and passes its currency to `CartView`. Storefronts that read an order's status for shipping read `fulfillmentStatus`, handle `disputed` and `paymentUnderReview`, and serve `/gift-cards/claim`.
4. Deploy from the same release: the publishing Workflow Worker first if the site uses one, then the site Worker. Then run the checks in the release checklist, and send again from the Stripe dashboard the `charge.dispute.created` event of every dispute that is still open.
5. Delete the `GALAXY_*` settings once the Worker log shows no deprecation warning and you no longer need to roll back to a pre-release Worker, which reads only those names.

Public commerce checkout remains disabled pending the separate [commerce launch gates](packages/plugin-ecommerce/PRODUCTION_READINESS.md).
