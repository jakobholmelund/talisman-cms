# Changelog

## Release candidate: talisman-cms 0.1.0 and plugins 0.0.1

- Initial publishable Talisman CMS packages for Astro and Cloudflare D1, with optional R2 media and KV caching.
- Draft, publish, archive, and restore transitions retain revisions atomically. Admin API clients now send `expectedRevisionId`; stale changes return HTTP 409.
- Media uploads accept bounded raster images validated by file signature. Legacy active uploads are served as downloads with restrictive headers.
- Collection access rules restrict native commerce tables to administrators. Cart and customer records are read-only in the generic CMS editor.
- Adds the analytics plugin and package archive checks to CI. Package manifests and archives use Apache-2.0.
- Adds `HybridAuthAdapter` (`talisman-cms/auth/hybrid`): local passwords for editors and Cloudflare Access SSO for allowlisted admins. The new `<adminPath>/sso` route (normally `/admin/sso`) verifies the Access JWT and issues the admin's CMS session; protect only that path with Access.
- Adds `talisman-cms/auth/identity`. Its `ensureVerifiedEmailIdentity` finds or creates the single CMS user for a verified email. New users get the `customer` role, which has no CMS access.
- Migration `0019_shared_customer_identity.sql` adds `galaxy_auth_session.auth_method` and `_ecommerce_customer_accounts.cms_user_id`, lowercases CMS user emails, and enforces one CMS user per email regardless of letter case. It links shoppers who have already verified their email to `customer` users. It fails if two CMS users' emails differ only by case; run the pre-check in the [release checklist](RELEASE.md) first.
- Shoppers can create an account with an email sign-in link before any purchase. Asking for a link creates no account: using it creates the account, already verified, or reuses the existing one, and links the shopper to the shared CMS identity. Links go only to a bare address. Each address can ask for three links per ten minutes and each source IP (IPv6 per /64) for 20 per hour, within a store-wide daily limit. Shopper sessions remain separate from CMS sessions.
- **Users** can change roles, disable, enable, and remove local accounts. In hybrid mode it adds editors, grants a verified shopper editor access with a password, and revokes CMS access instead of removing the shared identity.

### Breaking changes

These changes can break a site, integration or API client built against the pre-release source, for example through `link:` or a git checkout. Each entry says what to do; the sections below have the details, and [Upgrading](#upgrading) gives the order of the steps.

#### Deployment and settings

- Apply the new D1 migrations, `0019_shared_customer_identity.sql` through `0024_shopper_sign_in_tokens.sql`, before deploying the matching Worker, as the [release checklist](RELEASE.md#deployment-gate) describes. `0019` fails while two CMS users' emails differ only by letter case, and `0023` while two published entries in a collection share a slug, so run their pre-check queries first. Without `0019`, local and hybrid CMS sign-ins and shopper account reads fail; without `0021`, every entry read and save fails; without `0024`, shopper sign-in fails. `0022` moves global data that is not a JSON object under a `value` key (see [Site code and plugins](#site-code-and-plugins)).
- Worker settings, secrets and the default Workflow binding are renamed from `GALAXY_*` to `TALISMAN_*`, for example `TALISMAN_AUTH_SECRET` and `TALISMAN_PUBLISH_WORKFLOW`. The old names still work but log a deprecation warning. Rename each one and keep its value.
- The CMS no longer reads a `QUEUE` binding. `getClient().tasks.enqueueImageProcessing` and the `QUEUE` entry of `TalismanEnv` are removed; remove the calls, and the binding if nothing else uses it.
- Shopper sign-in email needs an email provider, normally a Cloudflare Email Service `[[send_email]]` binding named `EMAIL`, plus a sender (`TALISMAN_EMAIL_FROM` or `TALISMAN_COMMERCE_EMAIL_FROM`) and a public origin (`TALISMAN_PUBLIC_ORIGIN` or `TALISMAN_COMMERCE_PUBLIC_ORIGIN`). Built-in Resend support and `RESEND_API_KEY` are removed; register another HTTP email API as a custom provider.
- `DevAuthAdapter` fails `astro build` and `astro preview`, and refuses a dev server exposed with `--host` or `server.host`. Use `LocalAuthAdapter`, `HybridAuthAdapter` or `AccessAuthAdapter` for anything other than `astro dev` on localhost.
- CMS sessions end 7 days after sign-in, even while in use.

#### Packages

- `talisman-cms` requires Astro 7 (it accepted Astro 5 and 6 before) and Node 22.12 or later. `drizzle-orm`, `react` and `react-dom` are peer dependencies of the core, so the site installs them. Plugins take `talisman-cms` and `astro` as peers, plus React or drizzle-orm where they use them.
- `@talisman-cms/plugin-stripe/routes/*` resolves to built JavaScript in `dist/` instead of TypeScript source. Import `.../routes/webhooks`, without `.ts`.

#### Admin API clients

- Entry responses return `slug` as the slug being edited, which for a published entry can be a pending rename, and add `publishedSlug`, the live slug. Read `publishedSlug` for an entry's live URL.
- Entry slugs are unique within a collection, and client-chosen ids and slugs must follow the format rules. Creating an entry with, or renaming one to, a slug another entry uses or has pending returns HTTP 409, as does publishing onto a slug another published entry serves. A malformed id or slug returns 400.
- HTTP 409 no longer always means a stale edit: slug conflicts and unique or foreign-key constraint failures return it too. Reload only after a stale `expectedRevisionId` or `expectedUpdatedAt`, and otherwise show the response's `error`.
- With a publishing Workflow binding, a publish or archive that is still running after 10 seconds returns HTTP 202 with the entry as stored before the transition, `workflow: { status: 'pending', instanceId }` and a `message`, instead of an error. The Workflow finishes on its own; reload the entry to see the result.
- Validation errors return `{ error, fieldErrors, issues }`, with a summary in `error` instead of `Validation Error` (or `Validation failed` for globals). Required fields reject blank and whitespace-only values, and publishing validates the draft against them, so an entry saved with a blank required field must be completed before it can be published.
- An optional field sent as `''` is stored as no value: `NULL` in a nullable native column, the default or stored value in a `NOT NULL` native column that is not text, and `null` for an optional number or select in entries and globals. Read such fields as possibly `null`, not `''`.
- Client errors that returned HTTP 500 with the error's message now return 4xx: invalid JSON 400, an unknown collection, entry or revision 404, a constraint failure 409 or 400, and a body over 2 MiB 413. Other 500 responses and the health check no longer include error details; the Worker log has them.
- `GET .../entries/:id/revisions` returns revision metadata without `data`. Add `?includeData=true`, or load one revision with `GET .../revisions/:revisionId`.
- Globals return `data` as a JSON object instead of a JSON string, and `POST /admin/api/globals/:slug` rejects data that is not an object (400). Creating a global that is neither configured nor stored needs an administrator (403 for editors).
- Native collections: a create or update that sets a table column outside the configured `fields` returns 400 instead of storing it. Media records cannot be created through the entries API (403), and their `url` and `mimeType` cannot be changed (400).
- Auth API: in hybrid mode, password sign-in with an SSO admin's or a shopper's email returns 401 instead of 403. With `LocalAuthAdapter`, a `customer` account that has a password gets 401 and no session. A disabled account that signs in with its correct password gets 401, like a wrong password, instead of 403. Admin actions with a non-string `userId` or `role` return 400.

#### Site code and plugins

- `getClient().globals` returns `data` as an object, also for rows and cache entries written by earlier versions, which returned a JSON string. Remove any `JSON.parse` of it. Migration `0022` keeps stored data that is not an object, such as a list, under a `value` key, so code that read such a global reads `data.value`. `globals.create` and `globals.update` throw a `TypeError` for data that is not a JSON object instead of storing it.
- `getClient().entries.create` and `update` return `slug` as the slug being edited and add `publishedSlug`, and throw `SlugConflictError`, exported from `talisman-cms/client`, for a taken slug, also when they publish through a Workflow binding. In draft mode, `entries.findBySlug` finds an entry with a pending rename by its new slug only. Published reads are unchanged.
- When `entries.create` or `update` publishes or archives through a Workflow binding that is still running after 10 seconds, it returns the entry as stored before the transition with `workflow: { status: 'pending', instanceId }` instead of throwing. Check for `workflow` before treating the entry as published.
- Relationship fields resolve only entries of the relation's target collection, and leave ids of collections that only administrators may read unresolved.
- Deleting a media record deletes its file from R2. Pages that still use the file's URL get HTTP 404 once cached copies expire, which takes at most an hour now that media responses are no longer cached as immutable for a year. Replace a file's uses before deleting its record.
- Plugin endpoints without `public: true` (served under `<adminPath>/api/`) and plugin pages under the admin path need a CMS session: endpoints answer HTTP 401 and pages redirect to the admin sign-in. An endpoint that must stay public needs `public: true`, which serves it under `/api/`. Mark an admin-path page that anyone may open with `public: true` too; the `Plugin` type's `routes` items now declare it. Prerendering an admin-path page that needs a session fails the build.
- The admin SPA's browser copy of `virtual:talisman-cms/config` leaves out `runtimeHooks`, the `publishing` binding, and keys or values that look like secrets. Custom admin screens that need them read them on the server.
- The admin broadcasts `TALISMAN_ENTRY_SAVED` instead of `GALAXY_ENTRY_SAVED` on the `talisman-cms-preview` channel. `LivePreview` accepts both; custom preview listeners must accept the new type.

#### Ecommerce plugin

- Sign-in links carry the token in the URL fragment (`/account/verify#token=…`). Custom verify pages read it with `readCustomerSignInToken()` from `@talisman-cms/plugin-ecommerce/browser`.
- The account API returns HTTP 503 instead of 400 when a sign-in email cannot be sent. It also returns 503 once the new store-wide daily email limit is reached, and `requestCustomerEmailSignIn` then throws `CustomerEmailLimitError`.
- `GET` and `POST /api/ecommerce/cart` return only `{ id, items, locked }`. `GET` no longer creates a basket or sets the basket cookie; without a basket it returns `{ id: null, items: [], locked: false }`, and the `getCart` action returns `cart: null`.
- Baskets hold at most 50 lines of 1–99 units each. A new line must be a catalog product that is not archived, and its `variantId` must be a variant of that product. A product with variant groups needs one: a variant value, or a legacy group with no values. Otherwise the request gets HTTP 400, and checkout refuses such a line already in a basket with HTTP 409, so the storefront must let the shopper choose an option. Only `productId`, `variantId` and `quantity` are stored.
- `POST /api/ecommerce/discount` answers HTTP 503 `{ error: 'Checkout is disabled' }` unless `TALISMAN_COMMERCE_CHECKOUT_ENABLED` is `true`. Show a discount or gift card preview only when checkout is enabled.
- Sign-in link requests accept only a bare email address; send `jane@example.com`, not `Jane <jane@example.com>`. An address with a display name or several recipients gets HTTP 400.
- A used, expired or unknown sign-in link gets HTTP 400 with the error "This sign-in link is invalid or has expired." instead of "Sign-in link is invalid or expired". A verify page that compares the old text must check the status code instead.
- Asking for a sign-in link no longer creates a shopper account; the account is created, already verified, when the link is used. Code that looks for the account after `requestCustomerEmailSignIn` finds none until then.
- `firstOrderOnly` discount codes and referral awards now require a shopper with no purchase yet: no paid, fulfilled or refunded order (admin test orders do not count) under the checkout email, the signed-in account or an account with that email. They used to look at whether a shopper account existed for the email. A shopper who signed up or asked for a sign-in link but has not bought can now use a first-order code and be referred. With `0024` applied, the database checks the same rule when an order reserves a code. Review first-order promotions that relied on the old rule.
- `purgeStaleCommerceData` also deletes the shopper accounts that earlier versions created for every sign-in link request and that nobody used: never verified, not linked to a CMS user, at least a day old, and with no order, session, open basket, credit, referral or discount use. The first scheduled run after the upgrade removes them. Its result adds `signInTokens`, `unverifiedAccounts` and `rateLimits` counts. To see the candidates before that run: `SELECT id, email, created_at FROM _ecommerce_customer_accounts WHERE email_verified_at IS NULL AND cms_user_id IS NULL`.
- The basket and gift card cookies are named `talisman-cart` and `talisman-gift-<purchase id>`. The plugin still reads the old `galaxy-*` cookies, but site code that reads a cookie by name must use the names exported from `@talisman-cms/plugin-ecommerce/cookies`.
- The **Test checkout** screen, `/admin/api/ecommerce/test-checkout` and the simulated `admin_test` payment provider need `ecommercePlugin({ adminTestCheckout: true })`. `runtimePaymentAdapters(env)` no longer returns `admin_test`, and `reconcileCommerce` cancels `admin_test` orders left pending for more than 15 minutes.
- Removed the `InventoryDO` export and `bindCommerceApi().inventory.reserve()`, which reported success without reserving stock.

#### Stripe plugin

- `STRIPE_SECRET_KEY` (or `TALISMAN_STRIPE_SECRET_KEY`) and `TALISMAN_STRIPE_WEBHOOK_SECRET` are Worker secrets read at request time. The `stripeSecretKey` and `stripeWebhooksEndpointSecret` options in `astro.config` are ignored. Until the secrets are set, syncs fail and the REST proxy and webhook endpoint return HTTP 503.
- The public `/api/stripe/webhooks` endpoint is added only when `webhooksModule` is set or `webhookEndpoint: true`.
- Stripe IDs come only from the stored record. `stripeID` and `skipSync` values sent by the admin form or API clients are ignored, the hidden `stripeID` and `skipSync` fields are gone, and `stripeIdField` (default `stripeID`) names the field that holds the ID. A collection with a native table needs a column for it, or saves are refused.
- Deleting a record linked to Stripe needs the CMS admin role. Linked products and prices are archived in Stripe instead of deleted.

#### UI plugins

- daisyUI: the preview page and the theme and layout APIs need a CMS session, and the `glob-test` route is removed. Saving theme values outside the allowlist returns HTTP 400, and such values already stored are dropped when the theme is read or rendered. daisyUI and Starwind remove unsafe `href` and `src` values and inline styles from page-builder blocks.
- daisyUI: the Theme Builder, the `daisyui-theme` global and the theme injector use daisyUI 5 variables. Advanced values saved under daisyUI 4 keys (`rounded-box`, `rounded-btn`, `rounded-badge`, `border-btn`, `animation-btn`, `animation-input`, `btn-focus-scale`, `tab-border`, `tab-radius`) are ignored, so saved radius and border customisations fall back to the base theme's values. Enter them again in the Theme Builder's **Advanced Config** and save: `rounded-box` as **Radius: boxes** (`radius-box`), `rounded-btn` as **Radius: fields** (`radius-field`), `rounded-badge` as **Radius: selectors** (`radius-selector`) and `border-btn` as **Border width** (`border`). The animation, focus-scale and tab values have no daisyUI 5 counterpart. Colour overrides saved earlier are kept; if dark mode shows light colours, clear them with **Reset all**.

### Content and API

- Entries created outside the editor (seeds, imports, raw SQL) can now be edited and published. The first save or publish of such an entry records its stored state as revision 1 in the same batch, and the request may send `expectedRevisionId: null` or leave it out. Entries that already have revisions still need `expectedRevisionId`: a missing ID returns HTTP 428 and a stale one HTTP 409.
- Migration `0020_revision_baseline_and_globals.sql` adds a baseline revision for every entry that has none, pins the published revision of published entries, and unwraps globals stored as JSON text inside a JSON string. It only changes rows that still need it, so a rerun changes nothing.
- Published entries keep their live URL until they are published again. A slug change saved as a draft is stored as the entry's draft slug (new column `galaxy_entries.draft_slug`, migration `0021_entry_draft_slug.sql`). Admin API entry responses and `getClient().entries.create` and `update` return `slug` as the slug being edited and add `publishedSlug` (the live slug, or `null`). In draft mode `getClient().entries.findBySlug` finds an entry by its pending slug; published reads never include it.
- Entry slugs are unique within a collection. Creating an entry with, or renaming one to, another entry's slug or pending slug returns HTTP 409, and `getClient().entries.create` and `update` throw `SlugConflictError`, which `talisman-cms/client` exports. Publishing an entry whose slug another published entry already serves also returns 409. Saving with a blank slug keeps the current slug. Migration `0023_published_slug_unique.sql` adds a unique index so that only one published entry per collection holds a live slug; a publish that loses a race for it gets 409, or `SlugConflictError`. The migration fails while two published entries in a collection share a slug; the [release checklist](RELEASE.md#deployment-gate) has the query that lists them.
- Entry ids and slugs chosen by admin API clients are validated, with HTTP 400 on failure. Ids are 1–128 characters of letters, digits, `.`, `_`, `:` and `-`, start with a letter or digit, and may not be `new` or `all`. Slugs are 1–200 characters of letters, digits, `-`, `_`, `.`, `~` and `:`, with single `/` between path segments. An entry whose existing slug predates these rules can still be saved as long as the slug is unchanged.
- Entries whose id contains `:` or `.` can now be published through the Workflow binding, because Workflow instance ids are sanitised.
- Publishing through the Workflow binding checks the slug before it starts an instance, so a taken slug returns HTTP 409, or throws `SlugConflictError`, at once instead of timing out. `TalismanPublishWorkflow` does not retry a stale revision, a taken slug or a missing entry; the waiting request gets the same error as an inline publish (`RevisionConflictError`, `SlugConflictError` or `EntryNotFoundError`, all exported from `talisman-cms/client`). An instance that fails that way completes with `{ ok: false, error }` as its output. After a transition the Workflow Worker clears the entry's KV cache. The request waits up to 10 seconds (was 5); a publish or archive still running then returns HTTP 202 with the stored entry, `workflow: { status: 'pending', instanceId }` and a `message`, instead of a 500, and completes on its own. `getClient().entries` returns the same `workflow` field.
- `getClient()` publishes through the Workflow binding named by the integration's `publishing.workflowBinding` option; it always used the default name before.
- `getClient().entries.create` and `update` on native collections write the caller's data as given, so the table's own defaults still apply: no id is generated, and nothing is written to a text or other column that does not hold an integer timestamp. `create` fills a `createdAt` or `updatedAt` column only when it is an integer timestamp column (Drizzle `mode: 'timestamp'` or `'timestamp_ms'`) with no default and the caller passes no value; such a create used to fail on the `NOT NULL` column. `update` moves an integer `updatedAt` forward by at least one second, like the admin API, unless the caller passes `updatedAt`. It never writes the id column, and it skips the database update when nothing is left to write.
- Required text, textarea, select, date, color, media and single-relation fields reject blank or whitespace-only values, and required rich text fields reject empty documents. This applies on create, update and publish; publishing also validates the entry's draft against the collection's required fields.
- Validation errors for entries and globals return HTTP 400 with `{ error, fieldErrors, issues }`. `error` is a summary message instead of `Validation Error`, and `fieldErrors` lists messages by field name (a dotted path for nested fields).
- Other admin API client errors return 4xx instead of 500: invalid JSON or a body that is not a JSON object returns HTTP 400, an unknown collection, entry or revision 404, a database constraint failure 409 or 400, and a body over 2 MiB 413. Responses no longer contain SQL. Other failures return a generic HTTP 500 and are logged; messages thrown by collection hooks are still shown. The unauthenticated health check no longer returns error details.
- Globals are stored as a single JSON object. The API and `getClient().globals` always return `data` as an object, including rows and cache entries written by earlier versions. `POST /admin/api/globals/:slug` rejects data that is not a JSON object (HTTP 400), and `getClient().globals.create` and `update` throw a `TypeError` for it. Migration `0022_wrap_non_object_globals.sql` keeps stored global data that is not an object, such as a list, under a `value` key (`[1,2]` becomes `{"value":[1,2]}`).
- Only administrators can create a global. `POST /admin/api/globals/:slug` for a slug that is neither configured nor stored returns HTTP 403 for editors, who can still update configured and existing globals.
- Native collection updates accept `expectedUpdatedAt` and return HTTP 409 if the record changed since it was loaded. An update validates and writes only the columns it sends, and the response reports `updatedAt` as stored. Each update moves `updatedAt` forward by at least one second, so two saves in the same second no longer share a concurrency token and the stale one gets 409.
- An optional field left blank (`''`) by the admin form or an API client is stored as no value. Native tables get `NULL` in nullable columns, so a blank value no longer fails as "Expected number" or collides in a unique or foreign-key column; a `NOT NULL` column that is not text keeps its database default on create and its stored value on update. Optional number and select fields store `null` in entries and globals, and a blank required number reports "Required".
- Native (Drizzle-mapped) collections: the configured `fields` are the columns API clients may write. A create or update that sets another table column is refused with HTTP 400 naming the column, instead of the value being dropped silently; keys that are not table columns are ignored. Columns the admin editor sends back unchanged, the id column, `createdAt` and `updatedAt` are still accepted, and collection hooks can still set any column.
- Media records can no longer be created through `POST /admin/api/collections/media/entries` (HTTP 403); upload a file instead. A media record's `url` and `mimeType` cannot be changed after upload (HTTP 400).
- Deleting a media record deletes its R2 object and evicts this data center's cached copies. Media responses are cached for an hour (`Cache-Control: public, max-age=3600`) and revalidated with their ETag (HTTP 304), instead of for a year as immutable, under new edge-cache keys, so a deleted file stops being served everywhere within the hour. A failed upload no longer leaves an R2 object without a media record.
- Fields generated from native tables no longer mark `NOT NULL` columns that have a database default as required.
- `GET /admin/api/collections/:slug/entries` accepts `limit` (1–200) and `cursor`, and then returns `{ docs, nextCursor }`, newest first. Without `limit` it still returns the full array.
- Revision history: `GET /admin/api/collections/:slug/entries/:id/revisions` returns revision metadata without `data`. Add `?includeData=true` for full rows and `?limit=N` to shorten the list. The new `GET .../revisions/:revisionId` returns one revision with its data.
- `GET /admin/api/collections` no longer writes to D1 on each call. Collection rows are synced once per isolate, writing only missing or changed rows, and the listing takes a fixed few statements, with the row counts of all native tables from one statement. Configured globals are also created once per isolate.
- Relationship resolution queries related entries in chunks of at most 90 ids, so D1's limit of 100 bound parameters is never exceeded. It only matches entries in the target collection, leaves ids of collections that only administrators may read unresolved, and uses the deployed config's fields.
- Removed `getClient().tasks.enqueueImageProcessing` and the `QUEUE` entry of `TalismanEnv`. There was never a queue consumer.
- New `talisman-cms/richtext` export: `renderRichText(value, { headingOffset })` renders stored Tiptap JSON as safe HTML. It escapes all text, keeps only the editor's nodes and marks, and keeps only relative, http(s), `mailto` and `tel` links. A string value is shown as plain text. It also exports `richTextToPlainText`, `safeRichTextHref` and `escapeHtml`, and the core README has a section on rendering rich text.
- The ecommerce demo seed (`seeds/ecommerce-demo.sql`) stores post content as Tiptap JSON, so `renderRichText` shows it as formatted text instead of raw `<p>` tags. To fix posts seeded before this release, rerun `db:seed:ecommerce:local`. Opening and saving a post in the admin does not convert it: an HTML string becomes Tiptap JSON only when you edit the rich text field itself, save and publish.
- The KV cache is best-effort: a failed KV read or write falls through to D1 instead of failing the request. `getClient` accepts the request's execution context so cache fills finish after the response (inside the Worker it is otherwise taken from `cloudflare:workers`). A fill is dropped when the content it read was changed or hard-deleted while the read was in flight, so stale content is not cached for the TTL.

### Admin

- Entry editor: after the first save of a new entry, Save and Publish work without reloading (no more 428 "expectedRevisionId is required"), and publishing a new entry and then saving no longer returns 409.
- Entry editor: when a save is refused because the entry or record changed elsewhere (409), your edits stay in the form. You can load the latest version, copy your changes, or put back only the fields you changed. Other fields keep their latest values, so another editor's changes and stock reserved by checkouts are not overwritten. A refused Publish, Archive or Restore with no unsaved edits loads the latest version and asks you to retry.
- Entry editor: after a save conflict and **Load latest version**, the changes held in the conflict panel still count as unsaved. The **Unsaved changes** badge stays, leaving the page or closing or reloading the tab asks first, and **Dismiss**, Save, Publish, Archive and revision Restore ask before discarding them. **Load latest version** also keeps edits made after the conflict appeared, in the form or in raw JSON, and refuses to replace raw JSON that does not parse.
- Entry editor: rich text fields no longer count as edited when you only open, click into or tab through them, or when Tiptap reformats the stored content on load. The **Unsaved changes** badge and leave prompt stay quiet, and Publish no longer saves an extra draft first. After a save conflict the panel lists only the fields you actually edited, so **Put my changes back** no longer overwrites another editor's rich text that you only clicked into.
- Entry editor: rich text fields clear when the loaded version has no content, instead of showing the previous text.
- Entry editor: saving a native record, such as a product, sends the `updatedAt` it loaded, so stale saves are refused. Stock and inventory quantities are sent only when you change them, in the product form and in the options & stock section, so editing a product no longer overwrites stock that checkout has reserved. Native records no longer request revision history.
- Entry editor: optional number, select and relation fields left blank are saved as `null`, or left out of a new native record so the column default applies, instead of `''`. This stops "Expected number" errors, "A value is required" for a cleared **Inventory Quantity** on a new product, and 409s from blank unique or foreign-key values, such as a variant group saved with no option definition. The variant editor now clears SKU, image, price override and option definition when they are emptied.
- Entry editor: validation errors show readable messages (never "[object Object]") under each field, in the block inspector, and in a summary that names the field. Blocks with invalid fields are marked in the page outline. Server, network and expired-session errors are explained in plain words.
- Entry editor: warns before leaving or reloading with unsaved changes, and asks before restoring a revision over unsaved edits. Edits made in the raw JSON view are kept when switching back to the form.
- Entry editor: Publish and Archive no longer add an extra draft revision when there are no unsaved changes.
- Entry editor: media fields upload to and browse the media library under the configured admin path, and Browse loads the library once instead of sending requests in a loop.
- Collection lists load 50 entries at a time, with a **Load more** button. The revision history loads only the metadata of the latest 50 revisions.
- The media library and the media picker show the newest uploads first and load 60 and 48 items at a time, with **Load more**.
- Faster admin loading: related records load in parallel, 200 rows per request, and the collections list is reused for a minute. Saving no longer reloads the whole editor, and the variant editor reloads only its own tables.
- A published entry with a saved slug change shows its live address and the pending rename, in the collection list and under the editor's slug field, until the rename is published.
- Entry editor: only a stale edit opens the conflict panel. A slug another entry uses is reported at the slug field, and other refused saves, such as a unique-value or foreign-key clash, show the server's message.
- Entry editor: when a publish or archive is answered with HTTP 202 because its Workflow is still running, the editor shows the server's message and keeps Save, Publish, Archive and Restore disabled while it checks the entry, waiting 3, 6 and then 10 seconds between checks. It then reports that the entry is published or archived, or that it changed some other way, or offers a **Reload entry** button. A second click therefore no longer starts another Workflow instance.
- Entry editor: those checks only fetch the entry to see whether it has changed; they do not reload it into the form, so text typed during the server's wait or while the status shows is kept. When the transition lands, the entry is reloaded only if the form has no unsaved changes, and if the user starts typing during that reload, the form is left as it is. In both cases the notice says the unsaved changes are still in the form.
- Entry editor: the live preview broadcast for a publish or archive that is still running is sent once the transition has happened, not when the 202 arrives.
- `talisman-cms/ui/lib/entry-save.ts` adds `readPendingTransition`, `hasEntryMovedOn`, `describeSettledTransition`, `waitForPendingTransition` and `PENDING_TRANSITION_CHECK_DELAYS_MS` for a publish or archive that is still pending.
- Page builder: moving or removing a block no longer opens the Inspector.
- Accessibility: form fields and pickers have linked labels and linked error messages, and rich text toolbar buttons have names and an on/off state. The page builder Inspector is a modal dialog: focus moves into it, Tab stays inside, Escape closes it and focus returns. Collection and entry rows open from the keyboard, the **Users** confirm and reset forms receive focus, and the media upload can be reached by keyboard.
- Globals: saving a global with configured fields keeps the saved values in the form, so a second save no longer undoes the first, and the **Updated** time refreshes. Validation errors are shown next to each field and in a summary under the form.
- Globals: the raw JSON editor for globals without configured fields keeps what you type, saves exactly that document, keeps the **Saved** notice visible, and refuses JSON that is not an object with a clear message.
- Editors no longer see screens they cannot use: **New Global**, **Users**, **Ask Analytics** and the admin-only commerce tools. Opening one directly explains that admin access is required. The sidebar instead links editors to the commerce content collections they can edit.
- With hybrid auth, **Sign out** for Cloudflare SSO admins also ends the Cloudflare Access session. The button and the **Account** page say so, and a failed sign-out is reported. With Access auth, the "not authorized" screen offers a link to sign out of Cloudflare Access.
- **Users** reports a successful role change or access revocation as successful, shows server warnings (for example when existing sessions could not be ended), and refreshes the list after a failed action. It can re-enable a disabled account that no longer has CMS access, such as a disabled shopper account.
- The admin SPA's browser bundle gets a client-safe copy of `virtual:talisman-cms/config`. It leaves out `runtimeHooks` and their `args` and the `publishing` binding, and drops keys or values that look like secrets, with a build warning. Server code still receives the full configuration.
- Dev Toolbar: links follow the configured `adminPath`, and it lists your collections, globals and UI libraries and checks the `DB` binding live. The hard-coded collection and plugin lists, the "D1 + KV Active" status and the version label are removed.

### Authentication and users

- Sign-in rate limits are kept per client, keyed on `CF-Connecting-IP`, instead of in one shared bucket; `X-Forwarded-For` is ignored. The Cloudflare SSO sign-in is not subject to other clients' limits, so failed password attempts can no longer lock the SSO admin out, and it no longer rewrites the admin's stored credential on every sign-in.
- Password sign-in no longer reveals which emails belong to admins or shoppers. In hybrid mode an admin or shopper email gets the same HTTP 401 "Invalid email or password" as a wrong password, instead of a 403. With plain `LocalAuthAdapter`, a `customer` account that still has a password gets that 401 and no session. A disabled account gets the same 401 whether or not its password is right, instead of a 403 that confirmed the password.
- Admin actions reject a non-string `userId` or `role` with HTTP 400.
- CMS sessions end 7 days after sign-in, even if they are used continuously. The 12-hour inactivity timeout still applies.
- Plugin endpoints without `public: true` (served under `<adminPath>/api/`), and plugin pages under the admin path, now require a CMS session by default. API routes answer HTTP 401 JSON and pages redirect to the admin sign-in; a page opts out with `public: true`, which the `Plugin` type's `routes` items now declare. Prerendering an admin-path page that needs a session is a configuration error.
- `DevAuthAdapter` now fails `astro build` and `astro preview`, and refuses a dev server exposed with `--host` or `server.host`. It only signs requests in under the Vite dev server (`import.meta.env.DEV`) on a loopback host, never in a built Worker.
- First-admin setup with an email that already belongs to a shopper, or to any other account, returns HTTP 409 with a clear message instead of failing with 500.
- Fixed: changing a user's role (including **Revoke CMS access** in hybrid mode), resetting a password or disabling a user no longer returns a server error after the change is saved, and the user's existing CMS sessions are ended as intended. If ending them fails, the auth API returns 200 with a `warning` field, because the change itself was saved. Role changes and disabling still take effect immediately, and the warnings after **Disable** and **Revoke CMS access** no longer ask the admin to repeat the action.
- Enabling a disabled account, or granting a CMS role to an account without one (**Add editor** for a shopper, or `admin/set-role` in local mode), ends that account's existing sessions first. If they cannot be ended, the request returns HTTP 503 and nothing changes.
- A disabled account that lost CMS access keeps the `customer` role and can be re-enabled with **Enable** (`admin/unban-user`) without gaining CMS access; it gets none until an admin grants a role. **Add editor** on such an account while it is still disabled returns HTTP 409 and asks you to enable it first.

### Settings

- Worker settings and the default Workflow binding are renamed from `GALAXY_*` to `TALISMAN_*`, for example `TALISMAN_AUTH_SECRET`, `TALISMAN_ACCESS_*`, `TALISMAN_COMMERCE_*` and `TALISMAN_PUBLISH_WORKFLOW`. A `GALAXY_*` name is still read when its `TALISMAN_*` name is missing or blank, and the Worker logs a one-time deprecation warning. To migrate, rename each key and keep its value.
- New `talisman-cms/env` export for plugins and sites: `readSetting(env, name)` and `readBinding(env, name)` read `TALISMAN_<name>` and fall back to `GALAXY_<name>`.
- Setting values are trimmed, and a blank value counts as unset. A number or `true`/`false` in `wrangler.toml` `[vars]` is read as text, so `TALISMAN_COMMERCE_EMAIL_DAILY_LIMIT = 500` works; a list or table is ignored, with a one-time warning in the Worker log.
- The core README has a settings reference covering every `TALISMAN_*` setting, including `TALISMAN_COMMERCE_LOCAL_STRIPE_*`, and the Stripe and analytics settings.
- Live preview: the admin now broadcasts `TALISMAN_ENTRY_SAVED`. `LivePreview` accepts both the `TALISMAN_ENTRY_*` and the old `GALAXY_ENTRY_*` message types; custom preview listeners should switch to `TALISMAN_ENTRY_*`.
- The `galaxy_` database table prefix is internal and permanent; no migration is needed.

### Email

- New `talisman-cms/email` export, safe to import outside the Worker. It provides the `EmailProvider` interface, `EmailDeliveryError` (with a `code` and `retryable`), `sendEmail`, which blocks header injection and adds `Auto-Submitted: auto-generated` and `X-Talisman-Email` headers, `parseAddress`, the Cloudflare Email Service `send_email` provider, a console provider that runs only on localhost, `renderTransactionalEmail`, `escapeHtml` and `customEmail()`.
- New Worker-only `talisman-cms/email/runtime` export with `getEmailProvider(env)` and `sendConfiguredEmail(env, message)`. `TALISMAN_EMAIL_PROVIDER` chooses the provider (`cloudflare`, `console`, `custom` or `none`), configured by `TALISMAN_EMAIL_FROM`, `TALISMAN_EMAIL_REPLY_TO`, `TALISMAN_PUBLIC_ORIGIN` and `TALISMAN_EMAIL_BINDING` (default `EMAIL`). With the setting unset, a registered provider is used, then a binding named `EMAIL`.
- New `email` integration option registers a custom email provider: `talismanCms({ email: customEmail({ moduleId, exportName, args }) })` is validated when the config loads and served to the Worker as `virtual:talisman-cms/email`.

### Ecommerce plugin

- Shopper sign-in email goes through the Talisman CMS email provider, by default a Cloudflare Email Service `[[send_email]]` binding named `EMAIL`. Built-in Resend support and `RESEND_API_KEY` are removed; register Resend or another HTTP email API as a custom provider.
- The sign-in sender falls back from `TALISMAN_COMMERCE_EMAIL_FROM` to `TALISMAN_EMAIL_FROM`, and the public origin from `TALISMAN_COMMERCE_PUBLIC_ORIGIN` to `TALISMAN_PUBLIC_ORIGIN`. A trailing slash on the origin is accepted.
- Sign-in links carry the token in the URL fragment (`/account/verify#token=…`), so it never reaches the server or its logs. Use the new `readCustomerSignInToken()` from `@talisman-cms/plugin-ecommerce/browser`, which also accepts older `?token=` links and removes the token from the address bar.
- Asking for a shopper sign-in link no longer creates an account. The link stores only the token's hash and the address it was sent to, in the new `_ecommerce_sign_in_tokens` table (migration `0024_shopper_sign_in_tokens.sql`), and the account is created, already verified, or linked when the link is used. Unexpired links sent before the upgrade keep working.
- First-order discount codes and referral awards depend on purchase history (paid, fulfilled or refunded orders, not admin test orders) instead of on whether an account exists. Shoppers who signed up or asked for a link before their first purchase keep both, signed-in shoppers with no purchases can now be referred, and when two checkouts by the same shopper overlap, only the first one paid earns the award.
- New sign-in link preview: `POST /api/ecommerce/account` with `{ token, preview: true }` returns the masked address the link was sent to, such as `{ email: 'j•••@example.com' }`, without using the link. The browser helper is `previewCustomerSignIn(token)`. Previews are limited to 20 per hour per source IP (IPv6 per /64), apart from sign-in requests, and answer HTTP 429 beyond that. A used, expired or unknown link answers HTTP 400 "This sign-in link is invalid or has expired." to previews and sign-ins (it was "Sign-in link is invalid or expired").
- Sign-in link requests accept only a bare email address. An address with a display name or several recipients gets HTTP 400, and the link is always sent to exactly the lowercased address.
- The per-IP limits and the daily cap on sign-in emails are kept in the plugin's own `_ecommerce_rate_limits` table, so better-auth's cleanup of its own rate-limit table no longer deletes them.
- When a sign-in email cannot be sent, the account API returns HTTP 503 with a readable message instead of 400. Logs include only the provider's error codes, never addresses, links or tokens. Suppressed recipients get the normal accepted response.
- New store-wide daily limit on sign-in emails, `TALISMAN_COMMERCE_EMAIL_DAILY_LIMIT` (default 200). Once it is reached, the API returns HTTP 503 and `requestCustomerEmailSignIn` throws `CustomerEmailLimitError`. The per-IP sign-in limit counts IPv6 addresses per /64 prefix.
- `GET` and `POST /api/ecommerce/cart` return only `{ id, items, locked }`. The basket session token, account id and payment session id are no longer in the response.
- `GET /api/ecommerce/cart` no longer creates a basket or sets the basket cookie. Without a basket it returns `{ id: null, items: [], locked: false }`, and the first `POST` that adds items creates the basket. Cross-origin `POST`s no longer set the cookie either.
- The `getCart` and `clearCart` actions no longer create a basket either; `getCart` returns `cart: null` when there is none. `addToCart` validates the product before creating a basket and limits its input.
- `POST /api/ecommerce/cart` rejects bodies over 64 KiB (413), non-JSON bodies and a non-array `items` (400) before creating a basket. Posting an empty item list with no basket writes nothing.
- Baskets hold at most 50 lines (was 100) of 1–99 units each, exported as `CART_MAX_LINES` and `CART_MAX_LINE_QUANTITY`. A new line must be a catalog product that is not archived, and its variant must belong to that product; otherwise the request gets HTTP 400. Only `productId`, `variantId` and `quantity` are stored, and a rejected request creates no basket or cookie. New `carts.validateItems` checks an item list without writing.
- A product with variant groups can only be added to the basket or bought as one of its variants: a variant value, or a legacy variant group with no values. The cart API answers HTTP 400 `Cart items must choose one of the variants of <product id>` to a line without a variant or naming the group itself, and quote and checkout refuse such a line already in a basket with `Select an option for <product name>` (HTTP 409 from the checkout route).
- The checkout route and action, and the discount preview route (`POST /api/ecommerce/discount`), check `TALISMAN_COMMERCE_CHECKOUT_ENABLED` before anything else. While it is off, both routes answer HTTP 503 "Checkout is disabled", even to a request without a basket cookie or a cross-site or malformed one; the preview then reads no basket, account, discount code or gift card, and the action no longer sets a basket cookie.
- New `ecommercePlugin({ adminTestCheckout })` option, default `false`. The **Test checkout** screen, `/admin/api/ecommerce/test-checkout` and the simulated `admin_test` payment provider are added only when it is `true`; sites that use Test checkout must now set it. `startAdminTestCheckout(input, { adminPath })` supports a custom CMS admin path.
- `runtimePaymentAdapters(env)` returns only real providers (Stripe when configured) and never `admin_test`, and `createFromCart` chooses `admin_test` only when asked for it by name. Public order status checks and `reconcileCommerce` no longer mark a pending `admin_test` order as paid.
- `reconcileCommerce` cancels simulated `admin_test` orders left pending for more than 15 minutes, unless it is given `AdminTestPaymentAdapter`, so they no longer lock the admin's basket or keep the scheduled run from recovering real Stripe orders. A shopper can cancel a pending `admin_test` order from its basket (`cancelCheckout` or `POST /api/ecommerce/order`) without the simulated provider being registered.
- **Test checkout** no longer shows a stray "0" when the basket is empty.
- Removed the unfinished `InventoryDO` export and the `bindCommerceApi().inventory.reserve()` stub, which reported success without reserving stock. Checkout stock reservation in D1 is unchanged.
- New `purgeStaleCommerceData({ env, now?, batchSize? })` export from `@talisman-cms/plugin-ecommerce/api` for scheduled Workers. It deletes guest baskets idle for 30 days, shopper sessions a day after they expire or are signed out, email sign-in links, with the address they were sent to, a day after they expire or are used, shopper request counters whose window started more than a day ago, expired CMS sessions, and auth rate-limit rows older than 24 hours. It also deletes the shopper accounts that earlier versions created for every sign-in link request and that nobody used: never verified, not linked to a CMS user, at least a day old, and with no order, session, open basket, credit, referral or discount use. On a site upgraded from an earlier version, the first run removes those accounts. The result counts the deleted rows per step: `carts`, `customerSessions`, `signInTokens`, `unverifiedAccounts`, `rateLimits`, `authSessions` and `authRateLimits`. Deletes run in bounded batches, and the call throws if any step fails. Run it from your scheduled Worker next to `reconcileCommerce`.
- New `@talisman-cms/plugin-ecommerce/cookies` export with the basket and gift card cookie names (`talisman-cart` and `talisman-gift-<purchase id>`). Cookies set under the old `galaxy-cart` and `galaxy-gift-` names are still read, and a legacy basket cookie is adopted once.
- The shipped `CartBadge` and `CartView` components import their helpers by package name, so they work when installed from npm. `CartView` escapes its JSON data island, and `CartBadge` only reads the basket, so it no longer re-keys a signed-in shopper's basket.
- Commerce settings (checkout and gift card flags, Stripe mode and local test secrets, gift card key, referral defaults, email sender and public origin) are read as `TALISMAN_COMMERCE_*` and fall back to `GALAXY_COMMERCE_*`.
- `createCommerceCatalogSeedSql` gives each imported content entry a published baseline revision.
- The Shopper Accounts collection description now says shoppers share the CMS user for their email.
- The README has a quick start covering installation, registration options, bindings, migrations, `TALISMAN_COMMERCE_*` settings, the storefront pages and routes a site needs, the shipped components and helpers, and basket limits. It links to `PRODUCTION_READINESS.md` by its full GitHub URL, so the link works from the npm package.

### Stripe plugin

- Stripe secrets are read from the Worker at request time and never compiled into the server bundle: `STRIPE_SECRET_KEY` (or `TALISMAN_STRIPE_SECRET_KEY`, which takes precedence) and `TALISMAN_STRIPE_WEBHOOK_SECRET`. The `stripeSecretKey` and `stripeWebhooksEndpointSecret` options in `astro.config` are ignored with a warning.
- Syncs, the REST proxy and the webhook endpoint refuse to run until their secret is set. Saves that would call Stripe fail with a clear error, and the REST proxy and webhook endpoint return HTTP 503.
- The public `/api/stripe/webhooks` endpoint is added only when `webhooksModule` is set or `webhookEndpoint: true`. Signatures are verified with that endpoint's own signing secret.
- Stripe IDs are taken only from the stored record. `stripeID` and `skipSync` values sent by the admin form or API clients are ignored, and the plugin no longer adds hidden `stripeID`/`skipSync` fields to synced collections. The new `stripeIdField` option (default `stripeID`) names the field or column that holds the ID.
- Collections with a native table must have a column for the Stripe ID, and saves are refused without one. Previously the ID was dropped and every save created another Stripe resource.
- Deleting a record linked to Stripe requires the CMS admin role and a configured key. Linked products and prices are archived in Stripe (`active: false`) instead of deleted; customers are still deleted.
- The `./routes/*` export resolves to built files in `dist/`, and the package no longer ships or imports TypeScript source. Stripe calls use the fetch HTTP client, so they work in Workers.
- Adds a README covering installation, configuration, required secrets, what is synced, and security notes.

### Analytics plugin

- Sales, refunds and top products leave out Stripe test-mode orders only when `TALISMAN_COMMERCE_STRIPE_MODE` is `live`: orders whose Checkout Session id starts with `cs_test_`, and gift-card-only orders paid with a gift card bought in test mode. In test mode, the plugin-ecommerce default, they are included, so local and staging checkouts appear in Commerce analytics and Ask Analytics. Admin test orders are always left out.
- The Commerce analytics response and the Ask Analytics report's `commerce` data include `stripeMode` (`live` or `test`). The Commerce toolbar and the Ask report notes say whether Stripe test-mode orders are excluded or included.
- Refunds count on the date they were issued when the database has a `_ecommerce_provider_refunds` table, one row per provider refund. Net sales are then gross sales less the refunds issued in the period, and an order's provider refunds never count for more than its provider refund total, so a refund recorded twice is not counted twice. No migration in this release creates that table, so for now refunds count on the payment date of the refunded order. Both screens say which rule applies.
- Average order is gross sales per order, each Refunds figure shows how many orders were refunded, and the daily chart marks days where refunds exceed sales.
- Ask Analytics compares like with like. Today is compared with yesterday up to the same time, and this month with the same days of last month, or with all of last month once this month is longer. Yesterday, last month and the last 7 or 30 days are compared with the equal span before them. The summary names the exact window it compares with, and report date ranges show exact UTC times whenever a boundary is not at midnight.
- Ask Analytics: a Refunds report is summarized and compared by refunds and refunded orders, not net sales, and a Top products report names the best seller in each currency. Refund comparisons say what they compare: "USD refunds issued rose …" once refund dates are recorded, and until then the refunds on the orders paid in each window, as in "Refunds on USD orders paid in this period fell 90% compared with orders paid …". The refund metrics label the previous value "issued then" or "on orders paid then" to match.
- Ask Analytics: the example question "Did refunds increase compared with the previous 30 days?" is replaced by "Show refunds for the last 30 days".

### UI plugins

- daisyUI and Starwind: theme values are checked against an allowlist before they reach `<style>`, on save and again when rendered. Page-builder `href` and `src` values and inline styles are sanitised. The preview page and the theme and layout APIs require a CMS session, and the preview no longer loads the Tailwind Play CDN. The `glob-test` debug route is removed.
- daisyUI Theme Builder: saves only the colours and variables you change, and an empty field inherits the base daisyUI theme, so a first save no longer overwrites dark mode with a light palette or pins radius values site-wide. Switching a base theme clears that mode's colour overrides after a confirmation, each field has **Reset** and each mode **Reset all**, and saving is disabled while the saved theme could not be loaded or a value is invalid. **Open Full Preview** applies the unsaved values, through the same sanitiser, in place of the saved overrides.
- daisyUI Theme Builder: the defaults it shows are generated from daisyUI 5's 35 built-in themes, including silk, caramellatte and abyss. The new `pnpm run theme-defaults` script regenerates them, and the test suite fails when they drift. Advanced settings are daisyUI 5's `--radius-box`, `--radius-field`, `--radius-selector`, `--size-field`, `--size-selector`, `--border`, `--depth` and `--noise`; daisyUI 4 keys (`rounded-*`, `border-btn`, `animation-*`, `btn-focus-scale`, `tab-*`) are ignored. The `daisyui-theme` global declares all 20 colours per mode and these 8 variables, without default values.
- daisyUI Theme Builder: colour fields accept any allowed colour (hex, `oklch()`, `rgb()` and so on) without corrupting `oklch` values, and a bare hex value gets its `#`. The colour picker converts `oklch` to hex and sits over its swatch.
- daisyUI: the theme override CSS uses `[data-theme="<theme>"][data-theme]` rules and puts the advanced variables in each theme rule, and it is empty when nothing is overridden.
- daisyUI: new exports `DAISYUI_THEME_DEFAULTS`, `DAISYUI_THEME_DEFAULTS_VERSION`, `createThemeEditorState`, `themeEditorPayload`, `themeDefaultValue` and `colorToHex`.
- The daisyUI README documents its global, admin screen, endpoints, preview page and theme injector. The Starwind README describes what the package actually contains.

### Packaging

- `talisman-cms` declares `astro`, `drizzle-orm`, `react` and `react-dom` as peer dependencies and no longer bundles drizzle-orm. Plugins declare `talisman-cms` (`^0.1.0` when packed) and `astro` as peers, plus React or drizzle-orm where they use them. React is deduplicated for the admin SPA, which fixes a blank `/admin` under `astro dev` with installed packages.
- Packages are ESM-only, and each build clears `dist/` first. Manifests declare `repository`, `homepage`, `bugs` and Node `>=22.12.0` in `engines`.
- Every published package includes a `NOTICE` file with third-party attributions (daisyUI, shadcn/ui), a copy of the repository's root `NOTICE`. `pnpm release:check:archives` checks that each packed copy matches.
- Removed the `db:generate` script, `drizzle.config.ts` and the stale drizzle-kit snapshots. CMS migrations are hand-written SQL, and the published `drizzle/meta` folder holds only `_journal.json`. A new migration test applies the whole chain to an empty database and to one holding data from earlier releases.
- Publishing requires pnpm: `prepublishOnly` stops `npm publish`, which would ship unresolved `workspace:` ranges and no license text. Each package builds in `prepack`, so `pnpm pack` and `pnpm publish` always pack a fresh build.
- `pnpm release:publish` publishes every package with pnpm; run it with `--dry-run` first. The rebuild in `prepack` can reorder members in some `.d.ts` files, which stopped the next publish at pnpm's clean-tree check. The script and `scripts/check-dist-drift.mjs` now list those files and put them back, and the script fails when the build it packed differs from the committed `dist/`. Only a change of order within one union or one `{ … }` block is ignored; a union member or property that moves to another declaration, or any other change, fails the check.
- `pnpm release:verify` also packs every package, installs the tarballs into fresh Astro projects with npm and pnpm, builds them, imports every entry point, checks that `/admin` loads and that plugin-stripe's webhook route verifies signatures. Set `TALISMAN_SMOKE=0` to skip this step offline.
- CI: the committed `dist/` must match the build (`scripts/check-dist-drift.mjs`), and a new job fails on high or critical advisories in production dependencies (`pnpm audit --prod --audit-level high`).
- Refreshed transitive dependencies in the lockfile to clear high-severity advisories: browserslist 4.29.1, picomatch 2.3.2 and smol-toml 1.9.0.
- Added `SECURITY.md`: report vulnerabilities privately through GitHub security advisories.

### Upgrading

The release build is validated with Astro 7. To upgrade a site built on the pre-release source:

1. Make the code and configuration changes that the [breaking changes](#breaking-changes) call for.
2. Back up the D1 database, run the pre-checks, and apply the new migrations, `0019_shared_customer_identity.sql` through `0024_shopper_sign_in_tokens.sql`, as the [release checklist](RELEASE.md#deployment-gate) describes. The migrations folder also creates the ecommerce plugin's tables, so apply every migration a version ships even if the site does not use that plugin.
3. Add the `TALISMAN_*` settings and secrets with the values of their `GALAXY_*` names, the `EMAIL` binding if the site sends shopper sign-in email, and the Stripe secrets if it uses the Stripe plugin.
4. Deploy from the same release: the publishing Workflow Worker first if the site uses one, then the site Worker. Then run the checks in the release checklist.
5. Delete the `GALAXY_*` settings once the Worker log shows no deprecation warning and you no longer need to roll back to a pre-release Worker, which reads only those names.

Public commerce checkout remains disabled pending the separate [commerce launch gates](packages/plugin-ecommerce/PRODUCTION_READINESS.md).
